# Датасеты и репозитории с Python-кодом для CCRQS

Проверка источников на 11 ноября 2026 года. Основа поиска — аудит v5 (`dataset_audit_v5.csv`), [библиография главы 1](chapter1_literatura_v6.docx), заметки к литературному обзору (`research_2026-11-01/search_log.md`) и страницы авторов, репозитории и карточки данных. Включены источники, где есть исследуемый Python-код либо известен способ получить его по ревизии. Наличие готовых тестов и прогонов не было условием отбора. Числа ниже относятся к опубликованным выпускам и описаниям, а не к размеру будущей выборки. Ссылки и способ получения проверялись по опубликованным материалам, архивы целиком не скачивались, код не запускался.

Для пилота на реальных дефектах приоритетны **PyBugHive**, **BugsInPy** и **HaPy-Bug**. Для проверки ложных замечаний в контексте реальных PR — **SWR-Bench**. Для безопасности — **Vul4Py**, для небольших пар функций с готовым условием — **HumanEvalFix**. Локальный [QuixBugs](../../data/README.md) даёт 40 пар с исходником и эталоном для отладки конвейера.

## Репозитории для отбора правильного кода

Здесь доступны обычные Python-исходники. Для отрицательного контроля CCRQS следует зафиксировать, какое поведение проверено у конкретного фрагмента, и сохранить спецификацию или примеры использования. В случаях с правильными и ошибочными вариантами одной задачи их нужно учитывать вместе при разделении выборки.

| Источник | Где брать код |
|---|---|
| **TheAlgorithms/Python** | Самодостаточные реализации алгоритмов, часто с docstring и примерами. Подходит для коротких файлов и собственных тестов. [Репозиторий](https://github.com/TheAlgorithms/Python) |
| **more-itertools** | Функции и рецепты работы с итераторами, рядом документация и тесты. Подходит для проверки граничных случаев. [Репозиторий](https://github.com/more-itertools/more-itertools) |
| **CPython `Lib/`** | Исходники стандартной библиотеки. Для переносимых примеров выбирать функции, окружение которых можно восстановить в используемой версии интерпретатора. [Исходники](https://github.com/python/cpython/tree/main/Lib) |
| **Requests** | Python-исходники HTTP-библиотеки, например обработка заголовков, URL, параметров и ошибок. [Исходники](https://github.com/psf/requests/tree/main/src/requests) |

## Материалы из библиографии с ограниченной применимостью

- **Evaluating Large Language Models for Code Review** использует Python из HumanEval и модифицированные варианты. Код для этой постановки можно взять из HumanEvalFix и EvalPlus, отдельных размеченных исходников из этой работы в корпусе не учтено. [Cih25](https://doi.org/10.48550/arXiv.2505.20206)
- **Validation Evidence in LLM Repair Agents** публикует агрегируемые данные о проверках на уровне события, прогона и задачи. Для исходников следует обращаться к базовым SWE-датасетам. [Данные](https://doi.org/10.5281/zenodo.21642576), [Xu26](https://doi.org/10.48550/arXiv.2607.28871)
- **Benchmarking LLMs for Fine-Grained Code Review with Enriched Context in Practice** исследует многоязычные ревью, включая Python. Отдельный доступный пакет исходников в ходе проверки не подтверждён. [Статья](https://arxiv.org/abs/2511.07017)
- **ExcePy** описывает 180 багов встроенных типов Python, **PAMBench** — 670 случаев неправильного использования Python API. ## Что фиксировать при переносе примера в диплом

Достаточно сохранить источник и версию, URL проекта или задачи, SHA и путь файла при наличии, Python-исходник на вход модели, наблюдаемое поведение и происхождение эталонной метки. Для пары сохранить исправленный код или patch отдельно от входа. Отметить уровень проверки примера и наличие тестов, которые можно дописать позднее. Чтобы одна правка не оказалась в разных частях корпуса, сверять источник по репозиторию, коммиту, файлу и нормализованному diff, а для учебных программ — по задаче и идентификатору отправки.

Статические проверки закреплённых версий источников описаны в [аудите v6](../../audit/README.md).
