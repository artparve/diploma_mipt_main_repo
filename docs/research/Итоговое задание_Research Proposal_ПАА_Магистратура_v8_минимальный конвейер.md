# Аннотация
Исследование посвящено разработке и апробации формализованного подхода к оценке результатов автоматизированного code review, выполняемого локально запускаемыми open-source LLM-моделями. Подход учитывает обнаружение дефектов, релевантность и практическую полезность комментариев, а также корректность предлагаемых исправлений.

Цель исследования — создать воспроизводимую методологию сравнительной оценки таких систем на Python-коде с проверяемым ground truth. Предмет исследования составляют методы измерения качества ответов LLM в задаче code review и степень согласованности автоматических метрик с оценками разработчиков-экспертов. Исследовательская проблема заключается в отсутствии единого валидированного критерия, который объединял бы несколько аспектов качества code review и при этом сохранял интерпретируемую связь с экспертным суждением [1,2].

Исходный пул формируется из открытых датасетов с дефектами Python-кода. Значение около 8000 записей является предварительным ресурсным ориентиром отбора и не обозначает суммарный размер источников или число пригодных случаев. Аудит v5 устанавливает различия единиц данных и необходимость проверки пересечений между источниками; фактический объём определяется после экземплярной фильтрации, удаления дубликатов и проверки воспроизводимости. Сначала проводится пилот на 20–30 примерах кода и 3–4 моделях; для каждого примера должны быть доступны эталонное описание дефекта и исправление, скрытые от моделей во время генерации. Каждая модель формирует собственный комментарий к проблеме и предлагаемое исправление. Объём основного эксперимента определяется по результатам аудита, пилота и анализа статистической мощности.

Ожидаемый результат — критерий CCRQS (Composite Code Review Quality Score), объединяющий нормированные показатели обнаружения дефектов, качества комментариев и предлагаемых исправлений. Веса и интерпретационные пороги CCRQS определяются только на калибровочной части данных, после чего фиксируются и проверяются на независимой тестовой части. Целевым признаком валидности является сильная ранговая связь с экспертными оценками на тестовой выборке (гипотеза: коэффициент Спирмена ρ ≥ 0.75).

# Общее описание исследования

## Цель и задачи, исследовательский вопрос

### Цель исследования

Цель данного исследования заключается в разработке и научной верификации CCRQS — комплексного формализованного критерия качества автоматизированного code review, выполняемого локально запускаемыми open-source LLM-моделями [3]. Критерий должен объединить три аспекта: способность обнаруживать подтверждённые дефекты, релевантность и практическую полезность комментариев, а также корректность и применимость предлагаемых изменений [4].

Веса компонентов CCRQS подбираются на калибровочной выборке по степени согласованности с экспертными оценками, а затем фиксируются. Итоговая валидность критерия оценивается только на независимой тестовой выборке. Компонентные значения F1, метрики качества комментариев и Code Quality Improvement Score рассматриваются как измеряемые результаты, а не как заранее заданные условия включения модели в исследование.

Основная экспериментальная группа включает локальные open-source или open-weight генеративные модели, способные выполнять одну и ту же инструкцию и возвращать единый структурированный ответ. Статические анализаторы образуют отдельную контрольную группу, а закрытая коммерческая модель при наличии ресурсов может использоваться только как внешний baseline. Предварительный ресурсный ориентир отбора — около 8000 записей из нескольких открытых датасетов; это не подтверждённый объём. Окончательный объём определяется после проверки применимости, воспроизводимости, дубликатов и статистической мощности.

### Задачи исследования

1. Провести систематический анализ не менее 50 релевантных публикаций по оценке автоматизированного code review, LLM для анализа кода и статическим анализаторам; временная граница поиска — дата замораживания экспериментального протокола.
2. Выполнить аудит кандидатных датасетов, сформировать отдельный пилотный набор из 20–30 примеров кода с эталонными описаниями дефектов и исправлениями и основной корпус из прошедших проверку воспроизводимых случаев, разделённый по проектам на калибровочную и тестовую части.
3. Отобрать 3–4 локальные open-source или open-weight генеративные модели для пилота и до 6 моделей для основного эксперимента; закрытые коммерческие модели рассматривать только как необязательный внешний baseline.
4. Формализовать CCRQS на основе трёх нормированных компонентов: обнаружения дефектов, качества комментариев и качества исправлений; определить правила сопоставления ответов с ground truth, настройки весов на калибровочной выборке и последующей проверки на тестовой выборке.
5. Создать автоматизированный фреймворк для подготовки входных данных, запуска моделей и статических анализаторов, проверки предлагаемых patch, фиксации времени и ресурсов, расчёта метрик и подготовки данных для экспертной оценки.
6. Провести пилотный эксперимент, уточнить по его результатам размер основного корпуса и вычислительный бюджет, затем выполнить основной эксперимент. Мутационное тестирование проводить только Python-совместимыми инструментами и на объёме, подтверждённом пилотом.
7. Выполнить валидацию CCRQS с участием 15–20 разработчиков с опытом code review не менее трёх лет. Размер экспертной подвыборки определить анализом мощности с верхним рабочим ориентиром 500 случаев; для каждого случая получить не менее трёх независимых оценок.
8. Проанализировать результаты, неопределённость и ограничения применимости CCRQS и сформулировать практические рекомендации.

### Исследовательский вопрос

Какая комбинация нормированных компонентов и весовых коэффициентов CCRQS, настроенная на калибровочной выборке, обеспечивает максимальную согласованность с экспертными оценками качества code review и сохраняет эту согласованность на независимой тестовой выборке при сравнении локальных open-source LLM-моделей на Python-коде?

Исследовательский вопрос охватывает три компонента: точность обнаружения подтверждённых дефектов, релевантность и практическую полезность комментариев, а также качество предлагаемых исправлений [10]. Конкретные значения компонентных метрик, весов и интерпретационных порогов не задаются как известный заранее результат: они оцениваются на данных и проверяются без повторной настройки на тестовой выборке.

Дополнительно исследуется, меняется ли согласованность CCRQS с экспертами в зависимости от типа модели, категории дефекта, сложности кода и доступного контекста [11,12].

### Границы исследования

Положения этого раздела являются нормативной рамкой для остальных частей версии v7. Упоминание около 8000 примеров означает предварительный ресурсный ориентир отбора, а не измеренный размер исходного пула или заранее фиксированный размер итоговой выборки.

#### 1. Объект и предмет исследования

Объектом исследования является автоматизированное code review Python-кода, выполняемое локально запускаемыми open-source LLM-моделями.

Предметом исследования является качество результата такого code review, выраженное тремя наблюдаемыми компонентами:

1. обнаружение реально существующих дефектов;
2. релевантность и практическая полезность комментариев;
3. корректность и применимость предлагаемых исправлений.

Исследование оценивает не общее «качество модели» и не качество исходного кода само по себе, а качество конкретного ответа модели на стандартизированную задачу code review.

#### 2. Экспериментальная единица

Основной экспериментальной единицей является один воспроизводимый экземпляр дефекта (`review instance`), связанный с конкретной версией Python-проекта и содержащий:

1. исходный код до эталонного исправления;
2. файл или ограниченный набор файлов, относящихся к дефекту;
3. описание и локализацию эталонного дефекта, если они доступны в датасете;
4. эталонный исправляющий commit или patch;
5. тесты либо иное проверяемое подтверждение исправления.

Модели не передаются эталонный patch, текст исправляющего commit и результаты экспертной разметки. На вход модели подаются только анализируемый код, одинаковая для всех моделей инструкция и заранее определенный допустимый контекст проекта.

Основной уровень анализа — один дефект в одном изменяемом Python-файле. Многофайловые и репозиторные случаи допускаются как отдельная дополнительная группа и не смешиваются с основной выборкой без стратификации.

#### 3. Содержание задачи code review

От модели требуется сформировать структурированный результат, включающий:

1. перечень обнаруженных проблем;
2. для каждой проблемы — категорию, серьезность и место в коде;
3. краткое объяснение причины и возможных последствий;
4. предлагаемое изменение кода;
5. уровень уверенности модели.

Ответ без найденных проблем также считается допустимым результатом и сохраняется как пустой список замечаний. Формат ответа и правила сопоставления замечаний с эталонными дефектами описаны в контракте v4; их точные версии и контрольные суммы фиксируются до запуска пилотного эксперимента.

#### 4. Типы анализируемых проблем

В основной количественный анализ включаются проблемы, для которых существует проверяемый ground truth:

1. логические и функциональные дефекты;
2. ошибки времени выполнения и обработки исключительных ситуаций;
3. дефекты безопасности, если датасет содержит подтвержденную разметку или воспроизводимый тест.

Замечания по стилю, читаемости, сопровождаемости и code smells анализируются отдельно. Они не включаются в расчет точности обнаружения дефектов без независимой экспертной разметки, поскольку для них обычно отсутствует однозначный эталон.

Синтаксические ошибки могут использоваться как техническая контрольная категория, но не должны составлять заранее заданную долю основной выборки без подтверждения их наличия в исходных датасетах.

#### 5. Язык и программный контекст

Исследование ограничивается Python-кодом. Основной корпус должен быть совместим с Python 3.8 и выше. Если воспроизводимость отдельного проекта требует более ранней версии интерпретатора, такой пример либо исключается, либо помещается в отдельно маркированную legacy-группу и запускается в изолированном окружении.

Размер контекста для основной выборки ограничивается кодом, необходимым для понимания дефекта, и единым максимальным бюджетом токенов для всех сравниваемых моделей. Случаи, требующие анализа всего репозитория или превышающие общий бюджет контекста, оцениваются отдельно.

#### 6. Сравниваемые системы

Основную экспериментальную группу составляют локально запускаемые open-source или open-weight модели, способные следовать инструкции и формировать результат в едином формате. Модели, изначально не предназначенные для генеративного code review, включаются только при наличии адаптера или дообученной конфигурации, обеспечивающей сопоставимый выход.

Статические анализаторы используются как отдельная контрольная группа. Закрытые коммерческие модели могут использоваться только как внешний baseline и должны быть явно отделены от основной группы. Их результаты не используются для подтверждения вывода об эффективности локальных open-source моделей.

LLM-as-a-Judge рассматривается как дополнительный способ оценки согласованности. Основным источником валидации CCRQS остаются слепые оценки разработчиков-экспертов.

#### 7. Включение и исключение примеров

Пример включается в основную выборку, если:

1. доступен исходный Python-код до исправления;
2. существует проверяемый эталон дефекта или исправления;
3. дефект воспроизводится целевым тестом, эталонное исправление устраняет отказ, а регрессионные тесты доступны; случаи только с разметкой допускаются в отдельный анализ обнаружения и комментариев, но не в полный CCRQS;
4. он не дублирует пример из другой части корпуса;
5. объем необходимого контекста укладывается в установленный лимит.

Из основной выборки исключаются сгенерированный и vendor-код, нерелевантные изменения форматирования, примеры без надежного ground truth, невоспроизводимые случаи, межъязыковые изменения и утечки между обучающей, калибровочной и тестовой частями корпуса.

Разделение корпуса выполняется по проектам или репозиториям, а не случайно по отдельным фрагментам кода, чтобы снизить риск попадания сходного кода в разные части выборки.

#### 8. Масштаб исследования

Заявленные 8000 примеров рассматриваются как предварительный ресурсный ориентир отбора, а не как размер всех исходных датасетов или гарантированный объем итоговой выборки. Фактический объем определяется после аудита датасетов, удаления дубликатов, проверки воспроизводимости и оценки статистической мощности. Опубликованные размеры разных источников не суммируются без приведения к единой экспериментальной единице и проверки пересечений.

До основного эксперимента проводится пилот на 20–30 примерах кода с участием 3–4 моделей. Каждый пример должен содержать подтверждённый дефект, эталонное описание проблемы и эталонное исправление. Эталонные материалы используются только для оценки и не передаются модели. Для каждого примера модель должна сформировать собственный комментарий и предлагаемое исправление; отсутствие найденной проблемы сохраняется как отдельный измеряемый исход. Таким образом, пилот даст от 60 до 120 результатов model review, не считая контрольных анализаторов. Пилот должен проверить выполнимость протокола, качество ground truth, надёжность автоматического сопоставления результатов, время обработки и стоимость экспертной оценки.

#### 9. Результаты, не входящие в обязательный объем исследования

В обязательный объем не входят:

1. обучение новой базовой LLM с нуля;
2. полный анализ произвольных репозиториев без ограничения контекста;
3. оценка языков программирования, кроме Python;
4. сравнение коммерческих продуктов как основной предмет исследования;
5. утверждение универсальности CCRQS за пределами проверенных типов дефектов, датасетов и моделей.

#### 10. Рабочая формулировка области применимости результата

CCRQS разрабатывается как критерий сравнительной оценки структурированных результатов автоматизированного code review для воспроизводимых Python-дефектов с известным ground truth. Выводы исследования распространяются на проверенные модели, категории дефектов и условия эксперимента; переносимость критерия на другие языки, целые репозитории и закрытые промышленные системы требует отдельной валидации.

## Проблема, актуальность, новизна

Современная разработка программного обеспечения характеризуется возрастающей сложностью программных систем и растущими требованиями к качеству кода, что делает процесс code review критически важным компонентом обеспечения качества программного обеспечения [11]. Традиционный ручной code review, несмотря на свою эффективность в выявлении до 80% дефектов кода, сталкивается с существенными ограничениями: высокими временными затратами, субъективностью оценок и непоследовательностью результатов, особенно в крупных распределенных командах [13].

Внедрение больших языковых моделей (LLM) в процессы автоматизированного анализа кода открыло новые возможности для повышения эффективности code review [2]. Однако современные исследования демонстрируют значительные пробелы в методологии оценки качества работы LLM-моделей при анализе исходного кода [10]. Существующие метрики оценки, такие как BLEU и CodeBLEU, показывают низкую валидность при оценке качества code review, поскольку основаны на поверхностном сравнении с эталонными ответами и не учитывают функциональную эквивалентность кода [10].

Центральная проблема исследования заключается в отсутствии унифицированной формализованной методологии для комплексной оценки эффективности автоматизированного code review с использованием LLM-моделей . Современные подходы к оценке качества кода страдают от различных недостатков, включая отсутствие обоснованности (soundness), недостаточную поддержку оценки архитектуры программного обеспечения и ограниченные возможности оценки тестирования и инфраструктуры [14].

Особую остроту проблеме придает тот факт, что автоматизированные инструменты code review часто генерируют высокий процент ложноположительных результатов, что приводит к "усталости от предупреждений" и снижению доверия разработчиков к автоматизированным системам . Исследования показывают, что от 20.29% до 44.93% функций кода, генерируемых LLM-моделями, содержат смещения при обработке задач, связанных с чувствительными атрибутами [15].

# Обзор литературы

## Анализ источников

Автоматическое ревью кода — это процесс применения программных инструментов для анализа исходного кода с целью выявления ошибок, уязвимостей и отклонений от стандартов программирования. Современные технологии в этой области значительно продвинулись: от базового статического анализа до мощных AI-систем, основанных на больших языковых моделях (LLM). Основные направления автоматического анализа включают статический анализ, методы машинного обучения и решения на базе LLM.

Статический анализ остается ключевым элементом автоматизации, охватывая линтинг, форматирование и проверку типов. Так, ESLint позволяет находить и устранять проблемы в JavaScript-коде, интегрируясь с редакторами и CI/CD-средами, автоматически исправляя синтаксические ошибки. SonarQube применяет расширенные методы анализа для выявления багов, уязвимостей и "запахов кода" более чем в 30 языках программирования, предлагая подробные отчеты и тесную интеграцию с рабочими процессами. DeepSource проводит анализ кода при каждом коммите и pull request, классифицируя проблемы по категориям — безопасность, производительность, антипаттерны — и обеспечивая низкий уровень ложных срабатываний (менее 5%).

Модели машинного обучения позволяют оценивать качество кода на основе анализа предыдущих ревью, выявляя закономерности и определяя приоритеты. Обучаясь на исторических данных, ML-системы предсказывают потенциальные проблемы с использованием методов контролируемого обучения, глубоких нейронных сетей и графовых структур. Такие решения способны классифицировать код, находить типовые ошибки и предоставлять релевантную обратную связь, улучшая свою точность по мере накопления новых данных.

Наиболее передовые технологии автоматического ревью основаны на LLM. GitHub Copilot предлагает интеллектуальное автодополнение кода, поддержку диалогов на естественном языке и выполнение сложных задач программирования. CodeRabbit использует обучение с учетом пользовательской обратной связи для генерации подробных построчных комментариев с точностью до 95%, интегрируясь с VS Code, GitHub и GitLab. LLM-ассистенты обычно включают модули классификации, исполнения и проверки, что позволяет гарантировать обоснованность и безопасность предлагаемых изменений.

Среди промышленных решений можно выделить Qodo Merge с применением RAG-архитектуры для контекстных подсказок, а также такие инструменты, как Greptile, Codacy и другие узкоспециализированные продукты. Исследования показывают, что подходы, основанные на ML, повышают точность выявления ошибок до 85–95% и сокращают время отладки до 70%. Тем не менее, остаются нерешенные задачи — необходимость учета контекста, минимизация ложных срабатываний и интеграция автоматизации с человеческим участием для достижения наилучшего качества ревью.

Оценка качества ответов больших языковых моделей (LLM) представляет собой сложную задачу, требующую многоуровневого и контекстно-чувствительного подхода. В отличие от традиционных моделей машинного обучения с бинарными или числовыми результатами, выходы LLM варьируются по степени корректности, что делает их объективную оценку затруднительной. Современные метрики делятся на несколько ключевых категорий: автоматические количественные, ориентированные на человеческое восприятие, специализированные для отдельных задач и новые подходы, основанные на самих LLM.

Автоматические количественные метрики

Эти метрики позволяют быстро и объективно оценить текст, но могут игнорировать более глубокие аспекты, такие как креативность или стилистические нюансы. Они делятся на следующие группы:

1. Метрики качества языка и когерентности:
    1. Perplexity — измеряет степень неопределённости модели при генерации текста (меньшие значения свидетельствуют о лучшем качестве).
    2. BLEU — оценивает совпадения между сгенерированным и эталонным текстом, ориентируясь на точность.
    3. ROUGE — измеряет полноту, т.е. сколько исходной информации сохранилось в ответе.
    4. METEOR — учитывает точность, полноту и семантическую близость с учётом перефразирований и морфологии.
2. Метрики на основе эмбеддингов:
    1. BERTScore — применяет трансформерные эмбеддинги и косинусное сходство для оценки текстов.
    2. Семантическое сходство — количественно выражает степень смыслового совпадения фрагментов текста.
3. Дистрибутивные метрики:
    1. MAUVE — сравнивает распределения текстов, созданных человеком и моделью, с помощью кластеризации в пространстве эмбеддингов.

Семантические метрики:

1. Контекстуальная релевантность — оценивает уместность информации в заданном контексте с помощью LLM-оценки.
2. Семантическая когерентность — проверяет логическую связанность и развитие мысли в тексте.

С увеличением использования LLM в чувствительных областях возрастает значимость оценки их безопасности и этичности.

Метрики безопасности:

1. Обнаружение галлюцинаций — выявление фактически неверных или вымышленных утверждений.
2. FactualCorrectness — сравнение сгенерированных фактов с проверенной информацией.
3. LATTE — оценка токсичности ответов модели.
4. Метрики предвзятости — анализ различий в точности между различными демографическими или социальными группами.

Подходы, адаптированные к специфике предметной области или задачи, обеспечивают более точную оценку.

Метрики для генерации кода:

1. Функциональная корректность — проверка выполнения кода на наборе тестов.
2. Синтаксическая корректность — соответствие синтаксису языка программирования.

Несмотря на развитие автоматических методов, человек остаётся ключевым источником оценки нюансов качества текста.

Метрики человеческой оценки:

1. HumanELY — комплексный подход, включающий:
    1. Релевантность
    2. Покрытие
    3. Когерентность
    4. Вред
    5. сравнительную оценку
2. Беглость — естественность и гладкость языка.
3. Когерентность — логическая стройность текста.
4. Релевантность — соответствие ответов заданному запросу.
5. Фактическая точность — достоверность утверждений.

Инновационный подход, в котором LLM используются для оценки работы других LLM, объединяя точность человека с масштабируемостью машинной оценки. Метрики LLM-как-судья:

1. G-Eval — комбинирует выравнивание по контексту, логичность рассуждений и языковое качество.
2. Автоматизированная оценка релевантности — измеряет соответствие ответа заданному контексту.
3. Качественная оценка рассуждений — анализирует структуру и обоснованность логических выводов.

Современные тенденции в оценке LLM-систем демонстрируют переход от простых статистических метрик к более интеллектуальным, основанным на контексте и смысле. Метрики, такие как BERTScore, позволили лучше измерять семантическую близость, чем классические n-граммные подходы. Инструменты, построенные по принципу LLM-как-судья, например G-Eval, стремятся имитировать человеческую экспертизу при масштабной автоматической оценке. Однако наиболее надёжной стратегией остаётся сочетание различных метрик, адаптированных под задачу, с участием человека как эталона точности.

## Гипотеза исследования

**Основная гипотеза H1:** CCRQS, объединяющий нормированные показатели обнаружения дефектов, качества комментариев и качества исправлений, продемонстрирует на независимой тестовой выборке сильную положительную связь с агрегированными экспертными оценками качества code review: коэффициент ранговой корреляции Спирмена ρ ≥ 0.75.

**Дополнительная гипотеза H2:** CCRQS будет согласовываться с экспертными оценками не хуже любого отдельного компонента критерия; различие оценивается по bootstrap-доверительным интервалам корреляций.

**Гипотеза надежности H3:** на независимой тестовой экспертной подвыборке порядковая Krippendorff's alpha исходных целостных оценок H достигнет 0.80 при нижней границе 95%-го доверительного интервала не ниже 0.67. Это выбранное рабочее правило исследования, а не универсальная граница; оно фиксируется в v6 до основной разметки. Согласованность остальных шкал анализируется отдельно. Пилот не используется для подтверждения H3.

Веса компонентов и границы категорий качества («отличное», «хорошее» и т. п.) определяются на калибровочной выборке и замораживаются до анализа тестовой выборки. Универсальные числовые границы CCRQS заранее не задаются.

## Формальная спецификация CCRQS

### 1. Единица измерения и входные данные

Один балл CCRQS рассчитывается для пары `(пример кода i, модель m)`, то есть для **одного полного ответа code review**, включающего замечания, комментарии и предлагаемый patch. В пилоте используются 20–30 воспроизводимых примеров Python-кода; каждый содержит ровно один основной подтверждённый дефект, его эталонное описание, исходную версию кода, исправляющий patch и тесты. Если аудит обнаружит пример с несколькими независимыми дефектами, он исключается из пилота либо каждый дефект оформляется как отдельный экземпляр до предъявления модели.

Модель получает исходный код и заранее установленный контекст, но не получает эталонное описание, исправление, скрытые проверочные тесты и экспертные оценки. Она возвращает JSON-объект по [схеме v4](../../contracts/review_response_v4.schema.json) со списком замечаний. Каждое замечание имеет поля `file`, `line_start`, `line_end`, `category`, `severity`, `comment`, `proposed_patch`, `confidence`. Дополнительные поля в машинном ответе не допускаются. Для каждого примера сохраняются сырой ответ, разобранная структура, версия модели, prompt, параметры генерации и журнал запуска.

### 2. Сопоставление замечаний с эталонным дефектом

Перед расчётом балла каждое содержательное замечание модели сравнивается с эталонным дефектом по правилам раздела «Единый формат ответа модели и протокол сопоставления». Совпадение требует правильной **сути проблемы** и привязки к релевантному месту кода; дословное сходство с эталонным комментарием не требуется, поскольку для одного фрагмента возможны разные корректные формулировки [10].

Для пилота и основной экспертной подвыборки три независимых аннотатора размечают каждое замечание; разногласия разрешает отдельный четвёртый эксперт-арбитр после сохранения всех трёх исходных оценок. Из нескольких замечаний об одном дефекте только первое по порядку считается истинным обнаружением; повторные и неверные замечания считаются ложными срабатываниями. Дополнительный дефект, которого нет в исходном эталоне, оценивается отдельно по правилам подтверждения, чтобы его нельзя было автоматически назвать ошибкой модели. Если модель не нашла основной дефект, фиксируется пропуск. Один и тот же алгоритм применяется ко всем моделям.

Обозначения для одного ответа: `TP_i` — число замечаний, сопоставленных с основным эталонным дефектом (в пилоте 0 или 1); `FP_i` — число неверных, повторных и выходящих за поставленную задачу замечаний; `FN_i = 1 − TP_i` — число пропущенных основных дефектов. Подтверждённые независимые дефекты вне эталона учитываются отдельно как `additional_valid`: они не прибавляют `TP_i` и не прибавляют `FP_i`. Для нескольких основных подтверждённых дефектов потребуется однозначное сопоставление «одно замечание — один дефект»; это расширение не входит в пилот.

### 3. Компонент D: обнаружение дефекта

Для одного ответа используется F1 по замечаниям:

$$D_i = \frac{2TP_i}{2TP_i+FP_i+FN_i}. $$

Поскольку каждый пилотный пример содержит подтверждённый дефект, знаменатель положителен; если `TP_i = 0`, то `D_i = 0`. Ложные срабатывания снижают оценку даже при обнаружении настоящего дефекта. `D_i` лежит в интервале `[0, 1]`. Корпусные Macro F1 и Micro F1 рассчитываются и публикуются отдельно: среднее индивидуальных `D_i` не подменяет эти показатели.

### 4. Компонент C: качество комментария

Оценивается комментарий **того замечания, которое сопоставлено с эталонным дефектом**. Три независимых аннотатора выставляют по каждому признаку оценку `0`, `1` или `2`:

|Признак|0|1|2|
|---|---|---|---|
|Конкретность|Общее замечание без указания проблемы|Проблема названа, но локализация или условие неполны|Указаны конкретное место и условие возникновения|
|Корректность объяснения|Причина неверна или выдумана|Причина частично верна, но есть существенные пробелы|Корректно объяснены причина и возможное последствие|
|Полезность действия|Не ясно, что менять|Предложено направление без достаточной конкретики|Разработчик может выполнить конкретное действие по замечанию|

Для каждого признака берётся медиана оценок аннотаторов `c_{i,k} ∈ {0,1,2}`. Тогда

$$C_i = \frac{c_{i,1}+c_{i,2}+c_{i,3}}{6}. $$

Если сопоставленного замечания нет или комментарий пуст, `C_i = 0`. Содержание patch при оценке комментария аннотаторам не показывается, чтобы конкретность исправления не повышала оценку самого текста комментария. Оценки по отдельным признакам и согласованность аннотаторов сохраняются.

NDCG не является обязательной частью CCRQS в этом дизайне: она измеряет качество **ранжированного списка**, а не одного комментария. Её можно добавить как отдельный исследовательский показатель только при нескольких упорядоченных замечаниях и заранее размеченных уровнях релевантности; порядок замечаний должен быть получен от модели, а не отсортирован после оценки. Это соответствует определению NDCG в [документации scikit-learn](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.ndcg_score.html).

### 5. Компонент Q (Code Quality Improvement Score): качество предлагаемого исправления

Оценивается patch, связанный с сопоставленным замечанием. До запуска модели пилотный пример должен пройти проверку: исходная версия воспроизводимо не проходит хотя бы один целевой тест, эталонное исправление проходит его, а также имеется хотя бы один тест на отсутствие регрессии. Для patch модели вычисляются:

|Обозначение|Значение|
|---|---|
|`A_i`|1, если patch применяется к исходной версии и изменённый Python-код синтаксически корректен; иначе 0|
|`T_i`|1, если после patch проходят все целевые тесты, которые падали на исходной версии; иначе 0|
|`R_i`|Доля тестов, проходивших на исходной версии, которые продолжают проходить после patch; значение от 0 до 1|
|`S_i`|Медиана трёх независимых экспертных оценок смысловой корректности patch: 0 — неверное или опасное исправление, 0.5 — частичное или недостаточно подтверждённое, 1 — корректное и уместное|

Итоговый компонент качества исправления:

$$Q_i = A_i \cdot T_i \cdot R_i \cdot S_i. $$

Если подходящего patch нет, `Q_i = 0`. Если `A_i = 0` или `T_i = 0`, значение `Q_i` равно нулю и для этого patch не требуется отдельная экспертная оценка `S_i`. Проверка выполняется в изолированном окружении с зафиксированными версиями зависимостей. Отдельно сохраняются результат применения patch и каждый тестовый исход. Прохождение тестов само по себе не доказывает правильность исправления: patch может подстроиться под неполный набор тестов, поэтому в формулу включена смысловая экспертная проверка [17].

### 6. Итоговый CCRQS и веса

Все три компонента уже находятся в `[0, 1]`; нормализация по минимуму и максимуму на всей выборке не применяется. Итоговый балл:

$$CCRQS_i = w_D D_i + w_C C_i + w_Q Q_i,\quad w_D,w_C,w_Q \ge 0,\quad w_D+w_C+w_Q=1. $$

Следовательно, `CCRQS_i ∈ [0,1]`. Для **пилота** фиксируются равные веса `w_D = w_C = w_Q = 1/3`. По 20–30 примерам пилота веса не подбираются и вывод о достижении `ρ ≥ 0.75` не делается: пилот проверяет выполнимость измерения и ясность схем оценки.

После пилота веса подбираются на отдельной калибровочной части основного корпуса. Кандидаты перебираются по сетке с шагом 0.05 при ограничениях выше; выбирается комбинация с наибольшей средней корреляцией Спирмена с независимой целостной экспертной оценкой качества review при пятиблочной перекрёстной проверке по независимым группам репозиториев (`repo_group_id`, определённым в аудите данных). При равенстве выбираются веса, ближайшие к `1/3` для каждого компонента. Если калибровочная выборка содержит менее пяти независимых групп репозиториев или оценки не варьируются, остаются равные веса, а причина фиксируется. Выбранные веса, сетка и правило обработки связок замораживаются до открытия тестовых результатов.

Целостную оценку качества review эксперты дают по отдельной шкале `0–4`, видя исходный код и полный ответ модели:

|Балл|Якорь целостной оценки|
|---|---|
|0|Полезного review нет или ответ вводит в заблуждение|
|1|Есть отдельные верные наблюдения, но основная проблема не раскрыта и рекомендации ненадёжны|
|2|Основная проблема распознана частично; комментарий или исправление требуют существенной доработки|
|3|Проблема верно объяснена и предложено применимое исправление с небольшими недочётами|
|4|Проблема точно выявлена, комментарий конкретен, исправление корректно и пригодно к применению|

Эту оценку не вычисляют из `D`, `C`, `Q` и не показывают оценщикам значения компонентов. В пилоте, калибровочной и тестовой экспертных подвыборках целостную оценку H для каждого ответа дают три независимых эксперта. Эксперт H не выполняет сопоставление M и оценку C/S для того же экземпляра кода ни у одной модели. Разделение ролей обязательно для основной валидации; при нехватке участников результаты остаются пилотными. Это ограничивает круговую зависимость между построением критерия и его проверкой.

### 7. Неполные ответы и непригодные случаи

|Ситуация|Правило|
|---|---|
|Модель вернула пустой список замечаний или отказ|`TP=0`, `FN=1`, `D=C=Q=0`; случай остаётся в знаменателе|
|Есть замечание, но нет комментария|`C=0`; обнаружение и patch оцениваются по обычным правилам|
|Есть замечание, но нет patch|`Q=0`; обнаружение и комментарий оцениваются по обычным правилам|
|Несколько замечаний и patch|Для `D` учитываются все замечания; для `C` и `Q` берётся первое по порядку ответа сопоставленное замечание|
|Невалидная структура ответа при наличии текста|Фиксируется ошибка формата; содержательные замечания разбираются по заранее заданному правилу ручной разметки без переписывания ответа модели|
|Сбой инфраструктуры, тестов или окружения|После одной повторной попытки случай помечается `NA` и исключается из расчёта CCRQS; число таких случаев публикуется отдельно|
|Неоднозначный ground truth или нестабильный эталонный тест|Случай исключается до просмотра результатов моделей и заменяется заранее подготовленным резервным примером|

Отсутствие замечания или исправления является измеряемым результатом модели и оценивается нулём по соответствующему компоненту. Сбой среды регистрируется отдельно, чтобы его частота не искажала баллы моделей.

### 8. Агрегация и проверка критерия

Для каждой модели публикуются среднее и медиана `CCRQS_i`, средние значения `D`, `C`, `Q`, корпусные F1, доля пустых и невалидных ответов, доля применимых patch и число исключений `NA`. Доверительные интервалы рассчитываются повторной выборкой на уровне **независимой группы репозиториев** (`repo_group_id`), чтобы случаи из одного проекта, форков и связанных копий не считались независимыми.

В пилоте на 20–30 примерах отчёт содержит значения компонентов по каждому примеру, причины разногласий аннотаторов и оценку времени разметки. Небольшой пилот не служит основанием для окончательных порогов «хорошего» и «плохого» review.

В основной работе заранее зафиксированные веса применяются к независимой тестовой части один раз. Основной показатель валидности — коэффициент Спирмена между `CCRQS_i` и медианной целостной экспертной оценкой на тестовой экспертной подвыборке с 95%-м доверительным интервалом. Отдельно сравниваются три компонента, равновесовый CCRQS и настроенный CCRQS. При отсутствии достаточной экспертной разметки результат представляется как пилотная методика, без заявления о валидированном автоматическом критерии.

Экспертные значения `C_i` и `S_i` делают описанную версию CCRQS **формальной, но частично экспертной**. В пилоте 20–30 примеров оцениваются экспертами; до внедрения автоматического оценщика полный CCRQS рассчитывается только для экспертно размеченных ответов. Для расчёта на полном корпусе без человека потребуется отдельный автоматический оценщик комментариев и смысловой корректности patch, обученный или настроенный только на калибровочных данных и проверенный на независимой экспертной подвыборке. До такой проверки автоматические прокси публикуются отдельно и не подменяют экспертно проверенный CCRQS.

### 9. Контрольный пример расчёта

Для одного подтверждённого дефекта модель выдала два замечания: одно совпало с эталоном, второе оказалось ложным. Тогда `TP=1`, `FP=1`, `FN=0`, `D=2/3`. Медианные оценки комментария `2`, `1`, `2` дают `C=5/6`. Patch применился, целевой тест прошёл, 80% регрессионных тестов сохранились, а медианная смысловая оценка равна `0.5`: `Q=1·1·0.8·0.5=0.4`. При пилотных равных весах `CCRQS=(2/3+5/6+0.4)/3≈0.633`.

## Единый формат ответа модели и протокол сопоставления

### 1. Машинный контракт ответа

Канонический ответ модели — **ровно один JSON-объект без Markdown-обёртки и текста до или после него**. Его структура зафиксирована в [JSON Schema v4](../../contracts/review_response_v4.schema.json), основанной на официальной [спецификации JSON Schema Draft 2020-12](https://json-schema.org/draft/2020-12). Пример допустимого ответа находится в `review_response_v4.example.json`. Версия контракта в самом ответе — строка `"1.0"`.

|Поле|Тип и допустимые значения|Смысл|
|---|---|---|
|`schema_version`|Строка `"1.0"`|Версия структуры ответа|
|`issues`|Массив из 0–10 объектов|Замечания в исходном порядке модели; порядок сохраняется при оценке|
|`file`|Непустая строка|Путь к исходному Python-файлу относительно корня репозитория, с разделителем `/`|
|`line_start`, `line_end`|Целые числа ≥ 1|Включительные номера строк проблемного участка в **исходной** версии файла; `line_end ≥ line_start`|
|`category`|`functional`, `runtime`, `security`, `syntax`, `style`, `other`|Тип предполагаемой проблемы; основные классы эксперимента — первые три|
|`severity`|`low`, `medium`, `high`, `critical`|Оценка предполагаемой серьёзности проблемы|
|`comment`|Строка, в том числе пустая|Объяснение причины и последствий с предложением действия; пустая строка даёт `C=0`|
|`proposed_patch`|Unified diff или `null`|Исправление конкретного замечания; `null` означает отсутствие исправления и даёт `Q=0`|
|`confidence`|Число от 0 до 1|Уверенность модели; в базовый CCRQS не входит, но сохраняется для анализа калибровки|

Значения `functional`, `runtime` и `security` означают соответственно неправильный результат программы, ошибку выполнения и подтверждаемую уязвимость. `syntax` обозначает ошибку синтаксиса, `style` — замечание к оформлению, `other` — иной тип проблемы. Уровни серьёзности задаются как `low` — локальный ограниченный эффект, `medium` — сбой при обычном использовании, `high` — значимый сбой или риск для важных данных, `critical` — потенциально тяжёлый системный или эксплуатационный ущерб. Серьёзность указывает сама модель; в базовый CCRQS она не входит.

Все поля обязательны. Дополнительные поля не допускаются. Идентификатор примера, версия модели и время запуска присваиваются экспериментальным фреймворком, поэтому модель их не генерирует. Пустой список проблем представляется ровно так:

```json
{"schema_version":"1.0","issues":[]}
```

Каждый `proposed_patch` должен быть текстом unified diff с относительным путём к тому же файлу, который указан в `file`, и изменять только исходный код. Изменение тестов, конфигурации запуска или файлов окружения в patch не допускается. Если модель не может предложить исправление, она указывает `null`; не следует подставлять описание исправления вместо diff. Свободный текст `comment` должен быть на русском языке для единой экспертной оценки. Файл примера иллюстрирует ответ для функции `average(values)`, которая делит сумму на длину пустого списка.

### 2. Единая инструкция модели для пилота

Во всех запусках используется один шаблон. Переменные `{repo_context}` и `{source_code}` подставляет фреймворк, а их максимальный объём фиксируется до запуска пилота. Эталонный дефект, исправление и скрытые тесты в шаблон не попадают.

> Проведи code review предоставленного Python-кода. Найди функциональные ошибки, ошибки времени выполнения и подтверждаемые проблемы безопасности. Не добавляй замечания только о стиле. Для каждой найденной проблемы укажи файл, включительные номера строк исходного кода, категорию, серьёзность, комментарий на русском языке с причиной, последствием и предлагаемым действием, применимый unified diff исправления и уверенность от 0 до 1. Если не можешь предложить diff, укажи `null`. Верни только JSON по версии схемы `1.0`, без Markdown и дополнительного текста. Если проблем не найдено, верни `{"schema_version":"1.0","issues":[]}`. Не выводи более 10 замечаний. Контекст проекта: `{repo_context}`. Код: `{source_code}`.

Для всех моделей сохраняются одна версия текста инструкции, одинаковое правило формирования контекста и одинаковые ограничения на входные и выходные токены. Модель может использовать собственный механизм структурированного вывода, если он доступен, но содержательная инструкция и схема ответа остаются одинаковыми.

### 3. Последовательность проверки ответа

1. **Сохранить без изменений** сырой ответ модели и сведения о запуске. Самоисправление через повторный prompt в пилоте не применяется.
2. **Проверить JSON и схему.** Если весь ответ заключён в одну Markdown-кодовую секцию, допускается снять только её внешние маркеры; затем запустить синтаксический разбор и валидацию по JSON Schema. В отчёте отдельно отметить, что исходный ответ нарушил требование «только JSON».
3. **Проверить смысловые ограничения, которые схема не выражает:** существование `file` в разрешённом репозитории, отсутствие абсолютных путей и `..`, диапазон строк, условие `line_end ≥ line_start`, совпадение файла в diff и запрет на изменение тестов или файлов окружения.
4. **Проверить patch** на неизменённой исходной версии проекта: применимость, синтаксис, целевые тесты и регрессионные тесты. Patch каждого замечания проверяется отдельно; несколько patch одного ответа не накладываются друг на друга.
5. **Передать замечания аннотаторам** для сопоставления с эталонным дефектом и оценки комментариев и смысловой корректности применимых исправлений.

Структурная валидность (`schema_valid`) и смысловая валидность (`semantic_valid`) записываются раздельно. Если JSON не разобран, два аннотатора независимо извлекают из сырого текста только явно присутствующие содержательные замечания и точный текст diff, не исправляя формулировки модели; несовпадения разрешает третий аннотатор. Такой случай получает метку `format_invalid`, но найденный дефект всё равно может быть оценён. Неразборчивый отказ или отсутствие содержательных замечаний считается пустым ответом. Исходный текст остаётся доступным для аудита.

### 4. Правило сопоставления с ground truth

Три независимых аннотатора, не видящие название модели и значения CCRQS, для каждого замечания выбирают одну метку:

|Метка|Критерий|Влияние на `TP`, `FP`, `FN`|
|---|---|---|
|`primary_match`|Верно описан основной эталонный дефект: совпадают причина или условие отказа и место в коде либо непосредственно связанный вызывающий участок|Первое по порядку замечание даёт `TP=1`|
|`duplicate_primary`|Повторяет уже сопоставленный основной дефект без нового независимого содержания|Добавляет `FP=1`|
|`additional_valid`|Указывает другой реальный дефект из основных классов; истинность подтверждена воспроизводимым тестом или совместным экспертным разбором|Не меняет `TP` и `FP`; публикуется отдельно|
|`false_positive`|Причина неверна, указанной ошибки нет или замечание не подтверждается кодом|Добавляет `FP=1`|
|`out_of_scope`|Замечание касается стиля, синтаксиса или другой категории за пределами основной задачи пилота|Добавляет `FP=1` как нарушение инструкции|

Для `primary_match` недостаточно совпадения текста или только номера строки. Аннотаторы проверяют одновременно: (1) описано то же ошибочное поведение или причина; (2) указан правильный файл и участок дефектной логики либо его непосредственный вызов; (3) предложенное замечание относится к исходной версии кода. Точное совпадение границ строк не требуется. Если ни одно замечание не получило `primary_match`, `TP=0` и `FN=1`; иначе `FN=0`. При разногласии аннотаторы фиксируют обоснования, после чего отдельный четвёртый эксперт-арбитр принимает решение без информации о модели. Итоговый порядок `primary_match`/`duplicate_primary` проверяется на уровне всего ответа, а исходные метки не перезаписываются.

Метка `additional_valid` не расширяет эталонный набор посреди пилота. Все ответы моделей для того же примера проверяются на этот дополнительный дефект по единому правилу; его частота и влияние на выводы приводятся отдельно. Если обнаружится, что пример не соответствует критериям пилота или эталон неоднозначен, пример исключается для **всех** моделей и заменяется заранее подготовленным резервным случаем.

### 5. Контрольные случаи перед пилотом

До запуска моделей проверяются следующие случаи:

|Ответ модели|Ожидаемая обработка|
|---|---|
|`issues: []` при одном подтверждённом дефекте|`TP=0`, `FP=0`, `FN=1`, `D=C=Q=0`|
|Одно точное замечание, но `proposed_patch: null`|`TP=1`, `FP=0`, `FN=0`, `D=1`, `Q=0`|
|Одно точное замечание и одно неверное|`TP=1`, `FP=1`, `FN=0`, `D=2/3`|
|Два замечания об одном эталонном дефекте|Первое — `primary_match`, второе — `duplicate_primary`, `D=2/3`|
|Верное замечание без эталонной формулировки, но с той же причиной|`primary_match`; дословное совпадение не требуется|
|Patch применился и прошёл тесты, но смысловая проверка выявила неверное исправление|`S=0`, следовательно `Q=0`|
|Ответ в кодовой секции или с лишними полями|`format_invalid` фиксируется отдельно; содержимое разбирается по единому правилу|

Документы этапа 4 — эта версия proposal, [схема JSON](../../contracts/review_response_v4.schema.json) и пример ответа (`review_response_v4.example.json`). Их контрольные суммы и точные версии фиксируются перед первым запуском пилота; последующие изменения требуют новой версии спецификации.

## Методология исследования

### Методы исследования

1. Количественный метод:
    1. Тестирование всех моделей на одном и том же корпусе воспроизводимых случаев с известным ground truth.
    2. Расчёт компонентных метрик и анализ их связи с экспертными оценками на раздельных калибровочной и тестовой частях.
    3. Дополнительное мутационное тестирование для оценки чувствительности моделей к контролируемым изменениям Python-кода.
2. Качественный метод:
    1. Экспертные интервью и пилотная проверка схемы оценки для уточнения критериев полезного code review.
    2. Независимая слепая оценка результатов моделей несколькими разработчиками.
3. Смешанный метод:
    1. Сопоставление автоматических метрик, экспертных оценок и дополнительной оценки LLM-as-a-Judge.
    2. Анализ случаев расхождения между тремя источниками оценки вместо принятия judge-модели за эталон.

#### 4. Восстановление единого ground truth

Каждая исходная запись преобразуется в экземпляр дефекта с идентификатором `dataset:source_id`. Дубликаты сохраняют все исходные идентификаторы, но получают один канонический `instance_id`. Для допуска полного CCRQS пакет содержит:

1. канонический URL репозитория, SHA исходной и исправленной версий, относительный путь Python-файла и точные байты исходного кода;
2. основной дефект: `category` из контракта v4, строки **исходной** версии, краткое описание причины, условия отказа и последствия;
3. эталонный patch с отделёнными изменениями тестов, документации и конфигурации; перенос номеров строк из исправленной версии на исходную проверяется явно;
4. целевые тесты, которые воспроизводят дефект, и непустой набор регрессионных тестов, проходящих на исходной версии;
5. рецепт среды, версии Python и зависимостей, команды запуска, лимиты времени и сохранённые тестовые результаты;
6. происхождение и условия использования, результаты проверки дубликатов и назначенная часть корпуса.

Описание из датасета используется только после проверки на исходном коде. Если пригодного описания нет, два аннотатора независимо формулируют его по коду, исправлению и тестам; разногласие разрешается третьим. Эти материалы готовятся **до генерации ответов моделей**. Семантические метки, CWE и названия исключений отображаются в `functional`/`runtime`/`security` через документированное правило; неоднозначные случаи не получают категорию автоматически.

Строка diff сама по себе не доказывает место причины дефекта. Коммит с несколькими исправлениями допускается только после выделения одного независимого случая без потери необходимого контекста; иначе он маркируется как многофайловый/многодефектный и выводится из основной группы. Отдельный фрагмент без восстановленного проекта не выдаётся за воспроизводимый экземпляр проекта.

#### 5. Проверка воспроизводимости для компонента Q

Проверка проводится в изолированной среде с фиксированным снимком зависимостей. Требуется установить: хотя бы один целевой тест падает на исходной версии **из-за исследуемого дефекта**, тот же тест проходит на эталонном исправлении, все выбранные регрессионные тесты проходят на обеих версиях. Эталонный patch не меняет проверяемые тесты при сравнении; добавленные разработчиками тесты переносятся в отдельный оценочный набор, одинаковый для обеих версий.

До допуска выполняются три повторных прогона каждой версии в чистой среде с одним рецептом. Несогласованные исходы получают `flaky` и исключаются из основного корпуса. Timeout, недоступная зависимость и ошибка сборки регистрируются отдельно от воспроизведённого дефекта; неустранённые инфраструктурные проблемы не превращаются в «найденную ошибку». Любая адаптация среды фиксируется; изменение логики исходной программы ради прохождения проверки недопустимо.

Python старше 3.8 помещается в `legacy`; переносимость на современный интерпретатор не предполагается по названию датасета. Основная группа проверяется на конкретной поддерживаемой версии Python 3.8+ с записью её номера. Отсутствие целевого или регрессионного теста даёт `annotation_only` для отдельного анализа `D`/`C`; для такого случая `Q` и полный CCRQS не вычисляются и не подменяются нулём.

#### 6. Дубликаты и междатасетные пересечения

Проверка статьи PyResBugs выявила **прямой риск общего происхождения**: авторы объединяют 11 существующих наборов, а в перечне источников указаны BugsInPy и PyTraceBugs. Это подтверждает необходимость сравнения provenance, но не устанавливает число одинаковых записей в выбранных снимках. [Описание сбора PyResBugs](https://arxiv.org/html/2505.05777v1#S3.SS1).

Для всех источников последовательно проверяются: (1) канонический проект и исправляющий SHA; (2) SHA-256 исходного кода и эталонного patch; (3) сходство нормализованных токенов исходного и исправленного фрагментов. Точное совпадение хешей даёт кандидата в дубликаты; общий commit требует проверки, не исправлены ли в нём независимые дефекты. Для поиска близких копий рабочее правило — Jaccard ≥ 0.90 по множествам пяти-токенных шинглов Python-кода после удаления комментариев и пробельных токенов. Короткие фрагменты с менее чем пятью токенами сравниваются по полной токенной последовательности. Близость является основанием для ручного сравнения, а не автоматического удаления.

Хеш нормализованного AST можно хранить как дополнительный поисковый признак, но исходные байты и номера строк сохраняются. Форки, переименования и зеркала объединяются по истории происхождения. В журнале дубликатов указываются пара ID, использованный признак, решение, канонический ID и причина. Один дефект учитывается один раз, даже если у него несколько описаний, несколько функций или CI-заданий; несколько разметок HaPy-Bug являются оценками одного объекта, а не новыми примерами.

#### 7. Разделение корпуса без утечки

После дедупликации строятся `repo_group_id`: связанные репозитории, форки и подтверждённые близкие копии объединяются в компоненты связности. **Вся группа** назначается только одной части корпуса: `pilot`, `calibration` или `test`. Пилотный резерв принадлежит группам пилота; проекты пилота не возвращаются в основной test после настройки prompt и схем оценки.

Штатные `train`/`validation`/`test` PyTraceBugs не принимаются автоматически: группировка строится заново по восстановленному происхождению. Экземпляр без установленного репозитория не допускается к основной независимой проверке. Все 40 алгоритмов QuixBugs рассматриваются как одна группа одного benchmark-репозитория; их случайное распределение по calibration/test не считается разделением по проектам. QuixBugs остаётся отдельной технической группой вне подтверждения гипотезы на реальных проектах.

Сначала выделяются группы пилота и резерва, затем остальные группы распределяются между calibration и test. Размеры определяются после подсчёта пригодных случаев и анализа мощности; фиксированный процент сейчас не задаётся. Алгоритм распределения использует только метаданные, типы дефектов и фиксированный seed, без ответов моделей и экспертных баллов их качества. Проверяются непересечение `repo_group_id`, канонических ID, точных копий и подтверждённых близких копий. Для пятиблочной калибровки требуется минимум пять независимых групп calibration и отдельные test-группы; при нехватке применяется правило равных весов v4.

Разделение ограничивает утечку внутри эксперимента, но не доказывает отсутствие этих публичных данных в pretraining LLM. Публичность benchmark и доступность эталонных решений фиксируются как ограничение; повышенные результаты на известном QuixBugs не интерпретируются как доказательство переноса на новый код.

#### 8. Манифест экземпляров и подсчёт фактического объёма

Одна строка будущего `dataset_manifest` соответствует одному каноническому экземпляру. Источниковый CSV v5 не подменяет этот файл. Обязательные группы полей:

|Поля|Что фиксируется|
|---|---|
|`instance_id`, `dataset`, `source_id`, `source_aliases`|Канонический ID и все записи происхождения|
|`dataset_version`, `source_url`, `retrieved_at`, `artifact_sha256`|Версия/commit снимка, точная ссылка, дата загрузки и хеш артефакта|
|`repo_url`, `repo_group_id`, `buggy_sha`, `fixed_sha`, `file_path`|Проектная принадлежность и точные версии кода|
|`category`, `line_start`, `line_end`, `gt_description_path`, `reference_patch_path`|Подтверждённый основной дефект и скрытый эталон; пути к локальным материалам|
|`python_version`, `environment_path`, `target_tests_path`, `regression_tests_path`, `test_log_path`|Рецепт воспроизведения и результаты трёх прогонов|
|`source_sha256`, `patch_sha256`, `duplicate_cluster_id`, `dedup_status`|Проверка точных и близких копий|
|`dataset_license`, `project_license`, `license_evidence_path`, `license_status`|Условия использования конкретных материалов и основания решения|
|`input_context_path`, `context_budget_status`, `evidence_level`, `eligibility_status`, `exclusion_reason`, `split`|Контекст без эталона, допуск, причина исключения и часть корпуса|

Содержимое `gt_description_path`, `reference_patch_path` и оценочных тестов относится к закрытой от модели стороне оценки. Входные артефакты собираются из исходной версии отдельно; URL issue, сообщение исправляющего commit и traceback из эталонных материалов не добавляются в prompt v4. `split` пуст до распределения, затем принимает `pilot`/`calibration`/`test`/`technical`/`legacy`/`annotation_only`; `eligibility_status` — `pending`/`eligible`/`excluded`. Поля с неизвестными данными остаются пустыми с причиной, а не заполняются предположениями.

Для каждого источника публикуется поток отбора:

`N_snapshot → N_python → N_ground_truth → N_license → N_reproduced → N_scope_context → N_unique → N_eligible`.

Это **последовательные** числа оставшихся записей после соответствующего фильтра. До подсчёта фиксируется переход от исходной записи к экземплярам, включая объединённые и выделенные случаи, чтобы числа разных единиц не смешивались. Отдельно публикуются численность проектов/групп, `legacy`, `annotation_only`, `technical`, `pending` и исключения. Для каждого исключённого экземпляра сохраняется первая причина в порядке фильтров и все дополнительные обнаруженные причины; итог по первым причинам должен сходиться с разностью входа и выхода. Дедупликация считается на общем пуле, поэтому атрибуция исключённой копии исходному датасету сохраняется.

#### 9. Решение по корпусу и критерий готовности

Для пилота на **20–30 реальных дефектах** сначала проверяются BugsInPy-случаи из нескольких независимых проектов. При нехватке прошедших проверки случаев добавляются другие источники по тем же критериям; недостаток тестов не обходится включением пар кода без оракула. QuixBugs проверяет техническую работу patch и метрик отдельно. Безопасность включается только при достаточном числе подтверждённых воспроизводимых случаев, а её отсутствие отражается в области применимости результатов. Квоты по источникам и категориям до аудита экземпляров не назначаются.

**Завершено в v5:** сравнительная проверка шести источников по первичным материалам, выявление различий единиц и риска общего происхождения, проверка доступных лицензий, единые правила допуска, дедупликации, разделения и регистрации результатов. **Для завершения экземплярного аудита остаётся:** получить и зафиксировать снимки, заполнить манифест, проверить права конкретных материалов, выполнить локальные тесты, подсчитать пересечения и `N_eligible`.

Переход к генерации ответов разрешается протоколом только после готовности конкретного пилотного набора: подтверждены версии и происхождение, лицензии, основной дефект, стабильные целевые и регрессионные тесты, отсутствие утечки в контекст и пересечений между частями; подготовлен резерв и сохранены хеши манифеста и разбиения. Если это не выполнено, результат этапа остаётся аудитом источников и проектом правил отбора, без заявления о сформированном воспроизводимом корпусе.

## Протокол экспертной оценки

### 1. Объекты оценки и распределение ролей

Единица целостной оценки — полный ответ одной модели на один экземпляр кода (`review_id`). Замечания имеют исходный `issue_index` с нумерацией от 0 и производный `issue_id = review_id:issue_index`; это служебные поля разметки, а не новые поля ответа модели. Три независимые оценки означают оценки **трёх разных людей**, а не три повтора одним экспертом. Набирается целевой пул 15–20 разработчиков с опытом code review не менее трёх лет и подтверждённой практикой Python. Допуск к security-случаям требует соответствующей компетенции; эксперт может отказаться от незнакомого случая.

|Роль|Объект и шкала|Что показывается|Что скрывается|
|---|---|---|---|
|M: сопоставление|Каждое замечание; пять меток контракта v4|Исходный код, допустимый контекст, проверенный эталон дефекта, все комментарии в исходном порядке|Patch модели и эталона, модель/режим, confidence/severity, тестовые исходы patch, чужие оценки|
|C: комментарий|Первый итогово сопоставленный комментарий; три признака по 0–2|Исходный код, эталонное описание и точный текст комментария|Любой patch, сведения о модели, метрики и чужие оценки|
|S: смысл исправления|Patch сопоставленного замечания; 0/0.5/1 при A=T=1|Исходный код, patch модели, проверенное ожидаемое поведение|Эталонный patch, результаты тестов patch, модель/режим, confidence/severity, оценки M/C/H|
|H: целостное качество|Полный ответ review; 0–4|Исходный код, допустимый контекст, содержание всех замечаний и patch|Эталонное исправление, локализация эталонного дефекта, результаты тестов patch, модель/режим, confidence/severity, D/C/Q/CCRQS и чужие оценки|

H может получать одинаковую для всех моделей нейтральную спецификацию ожидаемого поведения без подсказки места и причины дефекта; её готовят до генерации, отдельно от эталонного описания. Под «полным ответом» в H понимается полное **содержательное** review: порядок, категории, пути, строки, комментарии и diff сохраняются, confidence/severity скрываются как самооценка модели. Сырой ответ хранится неизменным, а версия преобразования для экспертного предъявления фиксируется.

Внутри M/C/S один эксперт может выполнять несколько ролей; сначала фиксируются M и C, затем открывается S, чтобы patch не влиял на комментарий. Группа H не пересекается с M/C/S для одного `instance_id` по всем моделям. Минимальная схема назначения на экземпляр — три компонентных эксперта, три других эксперта H и отдельный доступный арбитр. Пропуск или нехватка компетенции замещается резервным экспертом; оценка не заменяется нулём. При отсутствии трёх завершённых оценок объект помечается `annotation_incomplete` и полный экспертно проверенный CCRQS не публикуется.

### 2. Критерии оценки и учебные примеры

Шкалы C, S и H в формальной спецификации выше являются каноническими; они повторены в самостоятельной [инструкции эксперта](../../contracts/protocol/annotation_guideline_v6.md) вместе с пятью учебными ситуациями. M оценивает совпадение причины/поведения и места, C — только качество текста выбранного комментария, S — смысл patch, H — весь результат review без вычисления компонентной суммы.

Альтернативный patch может быть корректным при отличии от эталона. Красивое объяснение не подтверждает обнаружение другого дефекта; короткий текст может получить максимальный C, если он конкретен, верен и даёт действие. Прошедшие тесты не гарантируют S=1. Отсутствующее замечание, комментарий или patch обрабатывается правилами v4, а не произвольной экспертной догадкой. Все учебные материалы синтетические и исключаются из исследования.

### 3. Слепой и случайный порядок

Координатор создаёт случайные `review_id`/`packet_id`, не содержащие названий моделей, датасетов или частей корпуса. Таблица соответствия моделям хранится отдельно и недоступна экспертам и арбитру. Из названий файлов пакета и метаданных убираются идентификаторы моделей. Содержательные самоидентификации в тексте заменяются только по заранее заданному правилу маскировки; каждое такое преобразование логируется, объяснение и patch не переписываются.

Для каждого эксперта фиксированный seed порождает отдельный порядок пакетов. Назначение сбалансировано по моделям и категориям при соблюдении ограничений ролей. Ответы разных моделей на один код не показываются рядом; между ними размещаются задания по другим экземплярам, если объём позволяет. Порядок замечаний **внутри ответа** не меняется, поскольку он определяет первое обнаружение. Эксперт не сравнивает ответ с соседним, не обсуждает незавершённые задания и не ищет готовое решение в сети.

До основной разметки сохраняются алгоритм назначения, seed, список экспертов по кодам, порядок заданий и хеши предъявляемых пакетов. Точные параметры и реализация фиксируются после пилота; v6 задаёт требования, но не заявляет, что распределение уже выполнено. Возможность узнавания модели по стилю остаётся ограничением слепого дизайна.

### 4. Самостоятельная оценка и разрешение разногласий

Эксперт сохраняет балл/метку, краткое основание с привязкой к коду, время и статус `completed`/`abstained`/`data_problem`. Исходные записи имеют версию и не перезаписываются. Чужие оценки открываются только после фиксации собственных и только участникам отдельного разбора.

Для M единогласная метка принимается после проверки обязательных свидетельств; любое расхождение передаётся четвёртому арбитру. Он изучает три объяснения и исходный пакет, фиксирует итоговую метку и основание. Для `additional_valid` требуется проверяемое свидетельство либо документированный экспертный разбор; голосование само по себе не подтверждает дефект. Итоговые метки всего ответа согласуются с исходным порядком: один первый `primary_match`, последующие повторы — `duplicate_primary`.

Для C, S и H основной результат — **медиана трёх независимых оценок**. Субъективное разногласие не заменяется согласованным баллом после обсуждения. Разброс 2 по признаку C, 1 по S или не менее 2 по H помечается `high_disagreement` для качественного анализа, но не отменяет медиану. Если разбор выявил ошибку пакета, неоднозначный ground truth или неверную версию кода, проверяется пригодность экземпляра для всех моделей: он исключается по правилам данных либо все затронутые задания повторяются с новой версией пакета. Первичные записи сохраняются как `superseded`; их нельзя выборочно исправлять только у неудобной модели.

### 5. Агрегация, пропуски и формальные нули

После итогового M рассчитывается D по неизменной формуле. По каждому из трёх признаков C отдельно берётся медиана трёх оценок, затем сумма делится на 6. Для S берётся медиана трёх оценок, затем Q=A·T·R·S. Независимый экспертный ориентир H — медиана трёх целостных оценок 0–4; он не вычисляется из CCRQS.

При пустом ответе или отсутствии `primary_match` D=C=Q=0 по протоколу; H всё равно оценивают три человека. Пустой комментарий даёт C=0 без трёх искусственных оценок. Отсутствующий patch, A=0 или T=0 даёт Q=0, а S получает `not_applicable`, а не три выдуманных нуля. Если A=T=1, S оценивается даже при R=0, чтобы правило отбора смысловых оценок было одинаковым. Системный сбой тестов остаётся отдельным NA, а отсутствие экспертной оценки — отдельным пропуском, без штрафа модели нулём.

### 6. Межэкспертная согласованность и проверка валидности

Согласованность вычисляется **до арбитража и агрегации** на исходных независимых оценках: nominal Krippendorff's alpha для пяти меток M, ordinal alpha отдельно для каждого признака C, для S и для H. Возможность работы alpha с несколькими экспертами, разными шкалами и пропусками описана в [методических материалах Криппендорфа](https://www.asc.upenn.edu/sites/default/files/2021-03/Computing%20Krippendorff%27s%20Alpha-Reliability.pdf). Ordinal alpha использует порядковую функцию расстояния выбранной реализации; обозначать обычную квадратичную разность как ordinal без проверки нельзя.

Формальные нули без человеческой оценки и `not_applicable` не включаются в матрицу надёжности C/S; публикуются размеры соответствующих подвыборок и основания отбора. Арбитражные метки, медианы и учебные примеры не подмешиваются к исходной матрице. При отсутствии вариации или ожидаемого расхождения alpha помечается как неопределимая, а не как 1. Вместе с alpha публикуются распределения баллов, доля полного совпадения, пропуски и разногласия.

Для интервалов применяется кластерный bootstrap по `repo_group_id`: 2000 выборок с возвращением, все ответы и оценки группы переносятся вместе, 95%-й percentile-интервал. Seed и реализация фиксируются до анализа. Число неопределимых повторов публикуется; при менее чем 1000 определимых повторов или менее чем пяти независимых групп интервал не используется для подтверждения H3. Значения alpha остаются описательными с указанием ограничения. Эти параметры — заранее выбранные правила v6, а не гарантии точности малого пилота.

ICC не является обязательным показателем для порядковых шкал и медиан. При дополнительном анализе обоснованных интервальных оценок заранее указываются модель ICC, absolute agreement/consistency, single/average measures и состав оценщиков; выбор зависит от дизайна. [Koo, Li, 2016](https://pmc.ncbi.nlm.nih.gov/articles/PMC4913118/). Разреженное назначение разных экспертов не выдаётся за полностью перекрёстный дизайн. Основная валидация CCRQS сохраняет корреляцию Спирмена с независимой H на test; Пирсон допустим только как дополнительный анализ с проверкой предпосылок.

### 7. Пилотная проверка схемы оценки и объём экспертной работы

Перед реальными заданиями эксперты проходят инструктаж на пяти синтетических примерах и тренировку интерфейса. Затем независимая разметка выполняется на результатах пилота из 20–30 экземпляров и 3–4 моделей, когда эти данные будут готовы по аудиту v5. Обсуждаются неясные якоря, причины пропусков, качество пакетов и время каждой роли. Изменённая схема оценки получает новую версию; затронутый пилот размечается заново без смешения версий. Схема оценки, распределение ролей и статистический план замораживаются до основной разметки; test не используется для их доработки.

Пилот даст 60–120 review. Только H потребует 180–360 независимых оценок. M потребует до 180–360 пакетов с оценкой всех замечаний, C — до 180–360 оценок выбранных комментариев, S — до 180–360 оценок прошедших A/T patch. Верхняя оценка — 720–1440 ролевых заданий, без обучения, арбитража и повторов; фактическое число зависит от пустых ответов и применимых исправлений. Рабочее время измеряется в пилоте по каждой роли и используется для бюджета основной экспертной подвыборки; 500 случаев не принимаются автоматически, а `case` здесь означает один ответ review.

Основная экспертная подвыборка выбирается отдельно внутри calibration/test по метаданным экземпляров с фиксированным seed до просмотра качества ответов. Для каждого выбранного экземпляра включаются ответы всех сравниваемых моделей, в том числе пустые и невалидные по формату; оценка H не отбирается по успешности patch. Ограничение C/S сопоставленными комментариями и прошедшими A/T исправлениями задаётся формулами, а не выбором удобных результатов. Список ID и правила замены непригодных экземпляров фиксируются до основной разметки.

### 8. Согласие, псевдонимизация и сохранение данных

До первого задания участник получает [форму согласия](../../contracts/protocol/expert_consent_v6.md): цель, порядок работы, приблизительную нагрузку, добровольность, право пропуска и выхода, условия хранения и публикации. Контакт исследователя, срок хранения, условия вознаграждения и крайний срок отзыва заполняются **до набора**, без выдуманных сведений. Дополнительное интервью требует отдельного добровольного согласия; аудио/видео не собираются по этой форме.

Во внутренних результатах эксперт обозначается случайным `expert_id`. Имена, контакты и подписанное согласие хранятся отдельно от разметки с доступом только у исследователя/координатора. Это псевдонимизация, пока существует таблица соответствия. Перед публикацией удаляются эта связь, контакты, точные временные метки и идентифицирующие сведения из свободного текста; опыт приводится диапазонами. Публичные результаты не содержат стабильного кода, позволяющего связать оценки конкретного человека между наборами. Участник заранее информируется, что после удаления связи отзыв его отдельных записей может быть технически невозможен.

### 9. Формат записи и готовность этапа

Учебный файл [expert_annotations_v6.example.json](../../contracts/protocol/expert_annotations_v6.example.json) показывает отдельные исходные записи M/C/S/H для одного синтетического review. Это не реальные оценки и не полная тройка оценщиков. Поля записи: `protocol_version`, `review_id`, `instance_id`, `packet_id`, `packet_version`, `assignment_id`, `expert_id`, `role`, `issue_index`, `ratings`, `rationale`, `status`, `duration_seconds`, `data_problem`. Сведения о модели и split хранятся в закрытой таблице координатора, вне формы эксперта. Арбитраж, агрегаты и автоматические A/T/R — отдельные сущности с ссылкой на исходные записи.

**Подготовлено в v6:** критерии оценки и инструкция с примерами, распределение ролей и доступа, минимум три независимые оценки, случайный порядок, арбитраж, учёт пропусков, анализ согласованности, шаблон согласия и формат данных. **Ещё не выполнено:** набор экспертов, заполнение административных полей согласия, техническое распределение заданий, пилотная проверка схемы оценки и измерение реальной согласованности. Подготовка материалов пункта 6 не означает, что экспертная оценка уже проведена или что аудит экземпляров v5 завершён.

## Эксперименты

### Задачи эксперимента:

1. Количественная оценка: Сравнить точность обнаружения ошибок между различными LLM-моделями
2. Качественная валидация: Определить соответствие результатов LLM экспертным оценкам разработчиков
3. Дополнительная оценка: сопоставить оценки отдельной judge-модели с экспертами без подмены независимой валидации CCRQS.
4. Ресурсная оптимизация: Адаптировать эксперимент под доступные вычислительные мощности

### Организация эксперимента

Локальные ресурсы:

1. Ноутбук (32 GB RAM): Подготовка данных, статистический анализ, качественная обработка интервью
2. Стационарный ПК (заявлено 6 GB VRAM): последовательный запуск компактных моделей с квантизацией и, при необходимости, частичным CPU-offload. Пригодность определяется по полной памяти весов, кэша и runtime, а не только по числу параметров; конфигурация и доступная RAM проверяются перед запуском.
3. Арендованный сервер: запуск моделей, не помещающихся в локальную память, и параллельная обработка после подтверждения необходимости пилотом.

Рекомендуемая конфигурация сервера:

1. GPU и объём VRAM: определяются после выбора моделей и измерения потребления памяти в пилоте.
2. CPU: не менее 8 ядер рекомендуется для подготовки данных и параллельного запуска тестов.
3. RAM: ориентир 64 GB для обработки корпуса и изолированных окружений.
4. Срок аренды и бюджет: рассчитываются по фактическому времени на один пример, полученному в пилоте.

### Экспериментальные и контрольные группы

1. Основная группа A — специализированные генеративные open-source или open-weight модели для кода, способные вернуть единый структурированный формат review.
2. Основная группа B — универсальные локально запускаемые instruct-модели с поддержкой Python-кода.
3. Основной набор пилота: Qwen2.5-Coder-7B-Instruct, Qwen3.5-4B в non-thinking text-only режиме и Ministral-3-8B-Instruct-2512 в text-only режиме; DeepSeek-Coder-6.7B-Instruct — кандидат на четвёртую модель или техническая замена. Состав, revisions и параметры фиксируются до генерации пилотных ответов; набор до 6 моделей основного эксперимента замораживается после пилота. CodeBERT/CodeT5 без адаптации не включаются.
4. Контроль 1 — Ruff, Pylint и Bandit с фиксированными наборами правил; Flake8 не запускается параллельно с дублирующими Ruff-правилами без отдельной причины. Сравнение выполняется по обнаружению подтверждённых дефектов в области правил; полный CCRQS анализаторам не приписывается.
5. Контроль 2 — слепые оценки 15–20 разработчиков с опытом code review не менее трёх лет.
6. Дополнительный внешний baseline — одна закрытая коммерческая модель при наличии ресурсов. Она не включается в основной вывод об open-source моделях.
7. LLM-as-a-Judge — отдельный исследовательский инструмент для вторичного анализа согласованности, но не замена экспертному ground truth.

### Выбор моделей и baseline

#### 1. Критерии отбора и смысл сопоставимости

Проверка выполнена **07.10.2026** по официальным model cards, документации разработчиков и инструментария. Выбор относится к воспроизводимому **однопроходному** review с JSON, русским комментарием и unified diff по контракту v4. Названия моделей определены сейчас; точные revisions, квантованные файлы и версии backend будут зафиксированы при техническом допуске. Публикуемые авторами benchmark-результаты не считаются измерениями в этом исследовании.

Модель включается, если доступны локальные веса с документированными условиями использования, генеративная post-trained/instruct-конфигурация, штатный chat template, достаточный текстовый контекст и воспроизводимый путь запуска. В реестре доступ обозначается как open-weight с лицензией весов; доступность данных и полного процесса обучения фиксируется как отдельная характеристика. Требуются три разных checkpoint для пилота и хотя бы две независимые семьи разработчиков. Следование русской инструкции проверяется технически, но утверждение о многоязычности не заменяет проверку качества комментариев.

Сопоставимость означает **одни и те же данные, задание, разрешённый контекст, схема, бюджет и число попыток**. Равенство размеров и обучающих корпусов не заявляется: выборка 4–8.4B содержит различия возраста, архитектуры и специализации. Две Qwen-модели не считаются независимыми семействами. По такому пилоту нельзя причинно заключить, что специализация на коде, новизна релиза или размер сами по себе объясняют преимущество; размер и конфигурация записываются как характеристики конкретной системы.

#### 2. Основной набор и кандидат на четвёртую модель

|ID и официальный checkpoint|Тип и проверенные характеристики|Почему выбран|Статус|
|---|---|---|---|
|L1 — [Qwen/Qwen2.5-Coder-7B-Instruct](https://huggingface.co/Qwen/Qwen2.5-Coder-7B-Instruct)|Специализированная causal instruct-модель для кода; 7.61B параметров по card; Apache-2.0|Компактная историческая опорная модель для code generation/reasoning/fixing; не называется новейшей моделью 2026 года|Основной кандидат; локально не запускалась|

|L3 — [mistralai/Ministral-3-8B-Instruct-2512](https://huggingface.co/mistralai/Ministral-3-8B-Instruct-2512)|Instruct-версия: 8.4B языковая часть + 0.4B vision encoder; официальный checkpoint FP8; Apache-2.0|Другая семья разработчиков и instruct-конфигурация; только текст, без reasoning-варианта|Основной кандидат; 6 GB VRAM не обещаны, требуется квантизация/допуск|
|L4 — [deepseek-ai/deepseek-coder-6.7b-instruct](https://huggingface.co/deepseek-ai/deepseek-coder-6.7b-instruct)|Специализированная causal instruct-модель класса 6.7B; собственная DeepSeek Model License|Вторая независимая семья code-моделей; исторический контроль либо замена технически недоступного основного кандидата|Не активна по умолчанию; включение фиксируется до пилота|

Основной план — **три модели L1–L3**, то есть 60–90 review на 20–30 экземплярах. При включении L4 получится 80–120 review. Исторические code-модели оставлены ради доступного локального сравнения, а актуализация обеспечивается современной L2 и L3. Это отбор по задаче и ресурсу, а не рейтинг лучших моделей.

Условия L4 проверяются по [лицензии весов](https://github.com/deepseek-ai/DeepSeek-Coder/blob/main/LICENSE-MODEL), отдельно от MIT-лицензии кода проекта. Для L3 нельзя описывать повторную квантизацию официального FP8 checkpoint как прямую BF16→Q4-конверсию: фиксируются точность исходного артефакта и все преобразования. Для мультимодальных L2/L3 отсутствие изображений не означает автоматически, что vision-веса выгружены; это подтверждается логом runtime.

Исключение по ресурсу не означает низкое качество модели. Крупные модели на сервере, agentic tool use, reasoning и разные способы retrieval не смешиваются с основной однопроходной группой. Если после пилота они нужны, создаётся отдельная версия протокола с соответствующими группами и затратами.

#### 4. Общий профиль запуска

Предварительные параметры v7 служат исходным профилем технического допуска. Они не являются измеренными оптимальными настройками и могут быть изменены **одновременно для всей группы** до генерации пилота с записью новой версии. После начала пилотной генерации настройки не меняются выборочно по неудачным ответам.

|Параметр|Общее правило|
|---|---|
|Режим|Один независимый вызов без инструментов, retrieval, self-critique и повторного prompt для исправления JSON|
|Инструкция и контракт|Точный текст v4, `schema_version="1.0"`; хеш prompt и JSON Schema записываются|
|Вход|Те же исходные файлы и текст контекста; лимит **4096 токенов полного входа**, включая chat template, проверяется каждым токенизатором|
|Выход|Не более **2048 новых токенов**; резерв контекста не менее 6144 позиций при указанном входном лимите; stop — штатные EOS/конец сообщения|
|Декодирование|Greedy, `do_sample=false`, temperature=0, без presence/frequency penalty; repeat penalty=1.0; seed=42 сохраняется, но не гарантирует битовую идентичность разных backend|
|Thinking и модальности|Отключённое thinking; только текст. У L2 применяется переключатель chat template, а не строка `/nothink`; исполнение выключения проверяется|
|Структурированный вывод|В основном профиле только prompt, без grammar/JSON-constrained decoding у всех моделей; format validity является измеряемым исходом|
|Веса и backend|Целевой профиль GGUF Q4_K_M в одной зафиксированной сборке llama.cpp; конкретные файлы и применимость ко всем архитектурам ещё не установлены|
|Ресурсы|Одна модель и один запрос одновременно, один компьютер для аппаратной группы; GPU-offload, cache dtype, CPU threads и занятая память фиксируются по каждой модели|

Разные токенизаторы дают разные числа токенов для одного текста. Поэтому не допускается отдельно обрезать контекст каждой модели: формируется единый вход, который укладывается в лимит **всех** участников. Неуместившийся экземпляр исключается/переносится до просмотра ответов для всех моделей одновременно. Общий числовой выходной лимит не обеспечивает одинаковое число символов; сохраняются оба размера и причины `finish_reason`, включая обрыв по лимиту.

Greedy выбран для одинакового простого режима, а не как утверждение об оптимальных рекомендациях производителей. Низкая schema validity, пустой ответ и ошибочный patch остаются результатами модели; это не причина удалить её из пилота. Техническая невозможность штатно загрузить checkpoint, применить chat template или обеспечить бюджет отличается от плохого review и регистрируется отдельно.

#### 5. Память, технический допуск и замена

В proposal заявлены 32 GB RAM ноутбука и 6 GB VRAM отдельного ПК; они не считаются памятью одной машины. До допуска фиксируются фактические CPU, GPU, свободные RAM/VRAM, ОС и драйверы компьютера, на котором будут выполняться генерации. Нижний арифметический ориентир для хранения N параметров по 4 бита — `N/2` GB в десятичной системе: около 2 GB для 4B, 3.8 GB для 7.61B и 4.2 GB для 8.4B **только языковых весов**. Q4_K_M не равен ровно четырём битам для каждого тензора; scale, служебные данные, vision-компоненты, кэш и буферы повышают реальную потребность.

[llama.cpp](https://github.com/ggml-org/llama.cpp) поддерживает квантизацию и смешанный CPU/GPU inference, но это не подтверждает успешный запуск выбранных файлов в конкретной сборке. GPU-offload допускается и логируется; если доля выгруженных на CPU весов различается, результаты времени/энергии относятся к конфигурации системы и не интерпретируются как чистое превосходство модели. Разные компьютеры образуют отдельные аппаратные группы.

Перед пилотом для каждого кандидата нужны: загрузка точного артефакта, проверка лицензии и хеша, штатный template, три синтетических задания на выдачу JSON/комментария/diff и один запуск с полным допустимым входным и выходным бюджетом. Эти задания не включаются в calibration/test и не используются для отбора по способности находить реальные дефекты. Проверяются корректное выполнение режима, поддержка архитектуры, отсутствие OOM, время и лог фактических параметров; генерация валидного JSON на всех учебных заданиях не является обязательным условием сохранения модели.

Если L1–L3 технически доступны, состав из трёх сохраняется; L4 включается только при заранее зафиксированном бюджете четвёртой модели. Если один основной кандидат недоступен, он может быть заменён L4 после той же процедуры. Если замена не даёт три сопоставимых участника, сначала корректируется общий ресурсный профиль или вычислительная группа; состав не выдаётся за завершённый пилот из трёх моделей. Замена после просмотра пилотных результатов требует новой версии и полного сопоставимого набора ответов, а не дозапуска только удачных случаев.

#### 6. Статические анализаторы как отдельный контроль

|Контроль|Область и предварительное правило запуска|Сравнение|
|---|---|---|
|[Ruff](https://docs.astral.sh/ruff/)|Основные диагностические правила F821/F823 для неопределённых/неинициализированных имён; стиль — отдельный отчёт. [F821](https://docs.astral.sh/ruff/rules/undefined-name/)|Обнаружение и локализация в области этих правил; одинаковый анализируемый Python-код|
|[Pylint](https://pylint.readthedocs.io/en/stable/user_guide/checkers/features.html)|Фиксированный профиль E0602/E0601; конфигурация проекта и target Python записываются. [E0602](https://pylint.readthedocs.io/en/stable/user_guide/messages/error/undefined-variable.html)|Отдельный контроль проверки имён; дубли между инструментами не считаются разными дефектами|
|[Bandit](https://bandit.readthedocs.io/en/latest/)|Security-плагины; точный список включённых B-правил и пороги severity/confidence фиксируются до пилота|Только подтверждённые security-случаи; сигнал инструмента сам по себе не является истинной уязвимостью|

Ruff выбран вместо отдельного параллельного Flake8 в пилоте, чтобы не дублировать одинаковые Pyflakes-проверки; наличие замены Flake8 описано в документации Ruff. Конкретные версии пакетов и полный конфиг сохраняются в реестре перед запуском; указание `latest` в экспериментальном lock-файле недопустимо. Область правил и случаи, на которых сравнивается полнота, определяются **до результатов**, а общий охват всех основных дефектов публикуется отдельно, без выбора только успешных классов.

Диагностика преобразуется адаптером в служебный объект `file`, диапазон строк, `rule_id`, текст и сопоставляемая категория. Сырой вывод остаётся доступен; severity/confidence из разных анализаторов не объединяются в общую шкалу. Для обнаружения применяются те же содержательные правила M и расчёт Precision/Recall/F1. C, S и полный CCRQS статических анализаторов в основной таблице обозначаются `not_applicable`, поскольку они не создают сопоставимое review с собственным объяснением и patch. Автоматические fixes анализаторов выключены; отдельная оценка autofix потребовала бы нового протокола.

#### 7. Коммерческий внешний baseline

Предварительно выбран один необязательный внешний кандидат — **Claude Sonnet 5.5**, ID `claude-sonnet-5-5`, подтверждённый в [официальном обзоре Anthropic](https://platform.claude.com/docs/en/models/overview). Это API-система с закрытыми весами: она не включается в вывод о локальных open-weight моделях и не требуется для завершения пилота. Доступ API и бюджет не проверены, вызовы не выполнялись; соответствующая запись реестра выключена.

При подключении сохраняются точный ID и версия по [правилам версионирования поставщика](https://platform.claude.com/docs/en/about-claude/models/model-ids-and-versions), дата, request/response metadata, поддерживаемые параметры и расход. Используются тот же prompt, текстовый контекст и 2048 выходных токенов; thinking/tools выключаются, если API это поддерживает. Отклонение по декодированию или невозможность выключить reasoning явно маркируется; такой результат не объединяется с локальной аппаратной группой. Цены проверяются в день расчёта бюджета, исторический прайс не фиксируется как постоянный.

#### 8. LLM-as-a-Judge как метод оценки

Отдельный необязательный кандидат — [Qwen/Qwen3-32B](https://huggingface.co/Qwen/Qwen3-32B), Apache-2.0, non-thinking. Он не входит в L1–L4 и не получает место в рейтинге авторов review. Из-за размера требуется отдельный проверенный ресурс; запуск на ПК с 6 GB VRAM не предполагается. Пока judge выключен, экспертная валидация CCRQS остаётся полноценной по v6.

Judge получает обезличенный экспертный пакет H и фиксированную шкалу оценки от 0 до 4, не видит модель-автора, confidence/severity, человеческие оценки, компонентные метрики и эталонный patch. Возвращает только служебные `score` и `rationale`; это **другая схема**, она не подменяет JSON review v4. Точный judge-prompt и реализация его формата фиксируются отдельно до дополнительного анализа. Он не назначает A/T/R, не разрешает экспертные споры и не используется для настройки test-весов CCRQS.

Сопоставляются judge-score и медианная H на той же заранее выбранной экспертной подвыборке через Спирмена, абсолютную ошибку по баллам и распределение разногласий. Повторные запуски при необходимости оценивают устойчивость judge, но не считаются оценками трёх разных экспертов. Родство judge с Qwen-участниками может вызвать family bias: результаты разбиваются по семье автора, а независимость от человеческой H не выводится из другого checkpoint. Если judge впоследствии включается как автор review, его собственные ответы исключаются из self-judging анализа или назначается другой judge до анализа результатов.

#### 9. Реестр, фиксация и результат этапа

[model_registry_v7.json](../model_registry_v7.json) содержит кандидатов, роли, первичные URL, предварительный общий профиль и незаполненные поля фиксации. Это **проект реестра**, не runnable-конфигурация и не отчёт о генерациях. `null` у revision/хеша/замеров означает непроверенное значение, а не нулевую память. По каждому активному участнику до пилота нужны:

- SHA checkpoint и tokenizer/template; источник, filename и SHA-256 фактически используемых весов;
- исходная точность, схема квантизации, преобразования и license evidence;
- backend commit/build, hardware group, offload и cache dtype;
- хеши prompt/схемы, реальные декодирующие параметры, input/output budget и seed;
- результат технического допуска, причина замены/исключения, пиковая память и время тестового запуска;
- точные версии/конфиги анализаторов; при внешнем API — ID, дата и журнал поддерживаемых параметров.

После заполнения создаётся отдельный frozen-реестр с хешем; неизменённый проект v7 сохраняется в истории. Бедный JSON или низкое качество ответа не скрываются корректировкой checkpoint, quantization или числа попыток на отдельных примерах. Оценки ресурсов замеряются отдельно от авторских характеристик model card.

**Завершено в v7:** актуализация по первичным источникам, конкретный основной набор из трёх моделей и кандидат на четвёртую, критерии сопоставимости, разделение четырёх ролей систем, проект общего профиля и реестр. **Ещё не выполнено:** загрузка/квантизация весов, фиксация revisions и backend, технический допуск, замеры памяти, API-доступ и генерация пилота. Следующий пункт 8 — реализация конвейера, в котором эти проверки станут исполнимыми.

#### Датасет и фактический технический допуск

Загружена Python-часть [QuixBugs](https://github.com/jkoppel/QuixBugs) из чистого локального checkout, commit `4257f44b0ff1181dedaedee6a447e133219fcebf`. Сохранены buggy/reference, тесты, JSON testcases, README, LICENSE и правовые примечания: 177 файлов с контрольными суммами. Проверены 40 задач и 40 различных хешей их buggy-файлов. Это контроль точных копий внутри снимка, не завершённая семантическая дедупликация общего корпуса.

Техническая приёмка выполнена на Windows с Python 3.12.14, pytest 8.3.5 и лимитом 2 секунды на тест. Допущена **31 задача**: имеются непустые группы падающих целевых и проходящих регрессионных тестов, reference проходит обе группы. **Шесть задач** исключены из Q из-за отсутствия проходящих регрессионных тестов: `minimum_spanning_tree`, `next_permutation`, `shortest_path_lengths`, `shortest_paths`, `topological_ordering`, `wrap`. **Три задачи** — `bitcount`, `find_first_in_sorted`, `sqrt` — не дали полного отчёта в этом окружении; тайм-аут Windows worker считается инфраструктурным исключением. Исходная и повторная попытки сохранены. Пропущенные slow-тесты не входят в знаменатель R.

QuixBugs остаётся **техническим контрольным набором** из одной группы `repo_group_id=jkoppel/QuixBugs`; здесь не создаются train/calibration/test и не оценивается переносимость на реальные проекты. Основной корпус из аудита v5 и требования к его групповому разделению сохраняются. Эти 31 задача не являются автоматически основным пилотом диплома и не заменяют экспертный ground truth. При смене окружения frozen-группы тестов повторно проверяются; исчезновение теста или изменение исходного поведения блокирует оценку экземпляра.

#### Prompt, ответ модели и сохранение запусков

Шаблон review скопирован из v7 без изменения текста. В него подставляются только buggy-код и нейтральные сведения о Python/файле; reference, целевые тесты и оценки в prompt не передаются. Для настоящей модели реализован адаптер локального llama.cpp: получение props, применение собственного chat template модели, токенизация и один запрос генерации. Параметры: temperature=0, seed=42, input≤4096 токенов, output≤2048, repeat_penalty=1, presence/frequency penalty=0, без grammar и без ремонта ошибочного JSON. Подлинный inference пока не выполнен; unit-тесты проверяют интерфейс с подставными ответами.

Конфигурация модели по умолчанию имеет допуск `not_run`. Перед настоящим запуском требуются точные revision и источник весов, SHA-256 весов и chat template, backend revision, фактическая команда сервера, описание оборудования и измерения памяти, проверенное отключение thinking. Модельный запуск разрешён только через контейнерный executor. Содержательный prompt одинаков; собственные templates и их хеши фиксируются отдельно. Не допускается индивидуальное усечение исходного текста для модели.

Конвейер сохраняет raw до разбора. Проверяются JSON Schema Draft 2020-12 и смысловые ограничения путей/строк; запрещены дублирующиеся JSON-ключи и нечисловые NaN. Одна внешняя Markdown-обёртка может быть снята с отметкой нарушения формата. Непарсируемый ответ остаётся `manual_extraction_required` для процедуры v4; он не отбрасывается и не получает придуманные замечания. HTTP-попытки, исходные payload/result и итоговый template prompt сохраняются. Транспортный сбой/HTTP 5xx допускает один зарегистрированный повтор; полученный плохой ответ модели повтор не вызывает.

#### Исполнение, анализаторы и первичные показатели

Каждый unified diff проверяется без shell и fuzzy matching: только один существующий Python-файл, совпадающий с `issue.file`, без абсолютного пути, `..`, смены тестов и настроек. После точного применения выполняется AST-проверка. **A** отражает применимость и синтаксическую корректность, **T** — прохождение всех frozen target-тестов, **R** — долю сохранившихся frozen regression-тестов. Пропавший/пропущенный ожидаемый тест и ошибка setup считаются инфраструктурой. Worker имеет лимит времени и один retry инфраструктурного сбоя; отчёты обеих попыток сохраняются. Исключения при будущем сравнении моделей должны применяться симметрично к одному instance.

В техническом профиле зафиксированы Ruff 0.11.2 (F821/F823), Pylint 3.3.6 (E0601/E0602), Bandit 1.8.3 (B102/B307/B602/B603/B604/B605/B606/B607/B608/B609, без фильтра severity/confidence), без autofix. Анализируется buggy-код и отдельно каждый исправленный вариант. Сохраняются исходные diagnostics/stdout/stderr, нормализованные пути/строки/rule_id/текст/категория, версии, команда и время. Категория из правила является кандидатом для M, а не подтверждением дефекта. Эти технические профили не замораживают основной эксперимент и не дают анализаторам полный CCRQS.

Режим `trusted_local` исполняет только доверенные технические фикстуры во временной копии и **не является системной песочницей**. Контейнерный adapter реализован с отключённой сетью, readonly исходниками/тестами и root filesystem, отдельным выводом отчёта, непривилегированным пользователем, ограничениями CPU/памяти/PID, снятыми capabilities и no-new-privileges. После process timeout контейнер принудительно удаляется. Dockerfile закрепляет `python:3.12-slim` по digest `sha256:05cda9777409a9c3ffddd94a4c476b79f0769a0b4857f0c7ed9226b6800b0d6f`; фактический Python в контейнере — 3.12.15. Контейнерные конфигурации закреплены по собранному image ID; `docker image inspect` сохраняется при каждом запуске. `.dockerignore` исключает датасет, результаты и venv из контекста сборки.

**Повторная проверка Docker — 07.10.2026:** после запуска Engine пользователем доступен Docker 29.7.2 (Linux x86_64). Реальный контейнерный прогон подтвердил UID=65534, CapEff=0, NoNewPrivs=1, запрет записи в файловую систему контейнера и тесты, блокировку исходящего соединения. docker_isolation_check.json (`dimploma_mipt/docker_isolation_check.json`) содержит результаты проверки и хеш worker; базовый образ и собранный image ID закреплены.

Первая контейнерная попытка выявила ошибку Ruff: создание кэша в readonly каталоге. В adapter добавлен `--no-cache`; затем повторены локальные и контейнерные прогоны. Итоговая проверка требует успешных статусов всех трёх анализаторов. Исходные отчёты сохраняются; docker_validation.json (`dimploma_mipt/docker_validation.json`) указывает успешные повторные запуски. Первоначальная неудача запуска Desktop сохранена в истории environment_check.json (`dimploma_mipt/environment_check.json`), предыдущая редакция v8 — в `dimploma_mipt/protocol/diploma_v8_before_docker.md`.

**Оставшееся ограничение:** настоящая LLM не запускалась; веса и технический допуск кандидатов v7 не подготовлены. Adapter llama.cpp проверен с подставными ответами. Контейнерный replay не является измерением качества модели.

**D/C/S/H требуют разметки v6.** Даже эталонный diff не получает автоматически `primary_match` или S=1. Когда A=T=1, S и Q остаются `null` до экспертов; для отсутствующего/неприменимого patch либо T=0 соответствующий issue имеет Q=0. Итоговый Q review вычисляется после сопоставления M, а не усреднением всех предложенных patch. Полный CCRQS остаётся `null`; валидный пустой review при измеримом baseline имеет D=C=Q=CCRQS=0 по исходному протоколу. Инфраструктура и отсутствие экспертной разметки не подменяются нулевой оценкой.

#### Результат этапа и переход к пилоту

Выполнены положительный и ошибочный **синтетические replay-прогоны**, каждый локально и в реальном Docker-контейнере, по трём задачам (`gcd`, `find_in_sorted`, `quicksort`). В положительном прогоне diff взят из reference: во всех трёх случаях A=1, T=1, R=1; Ruff/Pylint/Bandit успешно завершились для buggy и patch. В прогоне ошибок проверены пустой review, неприменимый diff (A=0, Q=0) и сохранение повреждённого JSON для ручного извлечения. SQLite каждого запуска содержит по три записи с `synthetic=true`. Успешные контейнерные запуски: `20261007T145204Z-59ffafb6` (эталонные patch) и `20261007T145228Z-36cb746b` (ошибочные ответы). Эти ответы не созданы LLM и не включаются в сравнение её качества.

Пройдены **24 теста конвейера**: пути и запрет изменения тестов, точные diff и несколько hunks, JSON/схема/внешняя обёртка, синтаксически неверный patch, отсутствие регрессионного результата, применение 31 reference-фикстуры, отсутствие reference/tests в prompt, ограничения inference и retry, параметры контейнера. Итоговая проверка доставки сверяет snapshot, manifest, SQLite, A/T/R и статусы анализаторов; доказательства и идентификаторы запусков сохранены в `verification.json`.

Следующий пункт плана — пилот. Контейнерное окружение проверено на трёх технических задачах. Перед настоящей модельной частью необходимы технический допуск весов/серверов кандидатов v7 и повторная приёмка выбранных экземпляров в закреплённом окружении; экспертные роли набираются по v6. Принятый объём пилота **20–30 экземпляров и 3–4 модели** сохраняется. Технический replay не является пилотом, не настраивает веса и не проверяет гипотезу корреляции CCRQS с экспертами.

### Фиксируемые переменные

1. Независимые переменные
    1. Модель и её версия: категориальная переменная.
    2. Размер модели: Непрерывная (количество параметров)
    3. Тип ошибки: категориальная переменная (логическая/функциональная, runtime/обработка исключений, безопасность; стиль анализируется отдельно).
    4. Сложность кода: Порядковая (низкая <10, средняя 10-20, высокая >20 по циклам Маккейба)
2. Зависимые переменные
    1. Точность (Precision): TP/(TP+FP) - доля правильно найденных ошибок
    2. Полнота (Recall): TP/(TP+FN) - доля обнаруженных ошибок от всех существующих
    3. F1-Score: Гармоническое среднее точности и полноты
    4. Время обработки: секунды на один пример.
    5. Качество комментария и исправления: нормированные компонентные оценки CCRQS.
    6. Ресурсоёмкость: пиковая память и, при доступности измерения, энергопотребление или стоимость запуска.
3. Контролируемые переменные
    1. Язык программирования: Python; основная группа — Python 3.8+, legacy-случаи маркируются отдельно.
    2. Формат входа, системная инструкция и схема ответа: единые для всех моделей.
    3. Максимальный объём передаваемого контекста и выходных токенов: единый общий бюджет.
    4. Параметры декодирования: фиксируются после пилота; предпочтителен детерминированный режим или одинаковая низкая температура и фиксированный seed.
    5. Версии моделей, анализаторов, зависимостей и тестовых окружений: фиксируются в журнале эксперимента.

### Процесс исследования

1. Этап 1: аудит данных и пилот (3–4 недели)
    1. Проверить структуру, лицензии, ground truth, воспроизводимость и пересечения кандидатных датасетов.
    2. Сформировать отдельный пилотный набор из 20–30 примеров кода с подтверждёнными дефектами, эталонными комментариями или описаниями проблем и эталонными исправлениями; стратифицировать его по подтверждённым категориям дефектов без навязывания заранее заданных долей.
    3. Запустить 3–4 модели и потребовать для каждого примера структурированный комментарий и предлагаемое исправление; отдельно запустить статические анализаторы и первичную версию расчёта метрик.
    4. Проверить применимость patch, устойчивость парсинга, время и ресурсы; определить необходимость сервера.
    5. Для мутационного тестирования использовать Python-совместимый инструмент, например mutmut или Cosmic Ray; объём подвыборки определить по итогам пилота.
2. Этап 2: подготовка и количественное тестирование (4–6 недель)
    1. Сформировать очищенный основной корпус и разделить его по проектам на калибровочную и тестовую части.
    2. Зафиксировать список до 6 моделей, их версии, prompt, схему ответа и параметры генерации.
    3. Получить ответы моделей и контрольных анализаторов, не раскрывая моделям эталонные исправления.
    4. Рассчитать компонентные метрики, время и ресурсоёмкость; сохранить сырые ответы и журналы выполнения.
3. Этап 3: экспертная оценка и настройка CCRQS (3–4 недели)
    1. Провести пилотную проверку схемы оценки и при необходимости полуструктурированные интервью с экспертами.
    2. Сформировать стратифицированную экспертную подвыборку; окончательный объём определить анализом мощности.
    3. Получить не менее трёх независимых слепых оценок для каждого отобранного результата review.
    4. Оценить исходную согласованность через nominal alpha для M и ordinal alpha для C/S/H до арбитража; ICC использовать только при обоснованном дополнительном дизайне.
    5. Настроить веса и пороги CCRQS только на калибровочной части и зафиксировать их до открытия тестовых результатов.
4. Этап 4: независимая валидация и дополнительный LLM-as-a-Judge анализ (2–3 недели)
    1. Однократно рассчитать CCRQS на тестовой части без изменения весов и порогов.
    2. Сопоставить CCRQS с экспертными оценками через корреляцию Спирмена; Пирсона использовать как дополнительный анализ при выполнении его предпосылок.
    3. Применить заранее выбранную judge-модель к той же экспертной подвыборке и сравнить её оценки с экспертами.
    4. Проанализировать систематические смещения по моделям, типам дефектов и уровням сложности.

## Обработка и анализ результатов

Метрики и способы фиксации данных

1. Точностные метрики:
    1. Precision, Recall и F1 на уровне сопоставленных замечаний.
    2. Macro F1 по подтверждённым категориям дефектов как основная агрегированная метрика обнаружения.
    3. Micro и Weighted F1 как дополнительные показатели влияния частоты классов.
    4. AUC-ROC или precision-recall curve рассчитываются только при наличии сопоставимой числовой уверенности модели.
2. Качественные метрики:
    1. Релевантность и полезность комментария по схеме экспертной оценки; NDCG применяется только при наличии явного ранжирования нескольких замечаний и graded relevance.
    2. Применимость patch, доля пройденных тестов, отсутствие регрессий и экспертная оценка исправления как основа Code Quality Improvement Score.
    3. Semantic Similarity между предложенным и эталонным исправлениями как дополнительная, но не определяющая метрика.
    4. Human Preference и Actionability для анализа практической полезности.
3. Инфраструктура фиксации данных
    1. MLflow или эквивалентный журнал для конфигураций, артефактов и метрик запусков.
4. База данных результатов:
    1. На пилоте — SQLite или Parquet; PostgreSQL подключается при подтверждённой необходимости масштабирования.
    2. Логические сущности: experiments, dataset_instances, model_predictions, issue_matches, expert_annotations и performance_metrics.
5. Статистическая валидация:
    1. Корреляция Спирмена между CCRQS и экспертными оценками — основной критерий валидности; Пирсона — дополнительный.
    2. Парный bootstrap или перестановочные тесты для доверительных интервалов различий между моделями.
    3. Friedman/Wilcoxon для связанных порядковых или непрерывных результатов; тест Макнемара — только для парных бинарных исходов.
    4. Поправка Холма при множественных попарных сравнениях.
    5. 95%-е bootstrap-доверительные интервалы для основных метрик и корреляций.
    6. Nominal/ordinal Krippendorff's alpha исходных независимых оценок с кластерным доверительным интервалом; ICC — только как отдельно обоснованный дополнительный анализ.

# Ожидаемые результаты

## Количественные результаты

Для каждой зафиксированной генеративной модели будут получены сопоставимые оценки Precision, Recall, Macro F1, качества комментариев, качества исправлений, времени и ресурсоёмкости. Для статических анализаторов публикуются показатели обнаружения в заранее заданной области правил, общий охват, время и ресурсы; C, S и полный CCRQS обозначаются `not_applicable`. Числовые диапазоны результатов заранее не задаются; для всех основных оценок приводятся доверительные интервалы и результаты анализа чувствительности.

Аудит определит фактический объём воспроизводимого корпуса и вклад каждого кандидатного датасета. Мутационное тестирование даст дополнительную, отдельно маркированную оценку чувствительности моделей к искусственно внесённым Python-дефектам.

## Качественные результаты

Экспертная часть должна дать проверенные критерии оценки релевантности, полезности и качества исправлений, а также оценку межэкспертной согласованности по методу, соответствующему числу экспертов и типу шкалы. Объём разметки фиксируется после пилота и анализа мощности, а не принимается равным 500 автоматически.

Будут определены области высокого и низкого согласия между моделями, статическими анализаторами, judge-моделью и разработчиками, включая различия по категориям дефектов и сложности кода.

## Центральный результат

Центральным результатом станет формально определённый CCRQS с зафиксированными весами, правилами расчёта, неопределённостью и областью применимости. Основная гипотеза подтверждается, если на независимой тестовой экспертной подвыборке коэффициент Спирмена между CCRQS и агрегированной экспертной оценкой достигает ρ ≥ 0.75 и его доверительный интервал не указывает на слабую связь.

LLM-as-a-Judge рассматривается как вторичный исследовательский результат. Его оценки сравниваются с экспертами на одной и той же подвыборке; заранее заданный диапазон корреляции не предполагается. Итоговые выводы должны включать не только статистическую значимость, но также величину эффекта, доверительные интервалы и ограничения переноса результатов.
