# Автоматический оценщик CCRQS

CCRQS — составной критерий качества ответа на задачу code review. Практический результат работы включает датасет, дообученную LLM для оценки обнаружения дефекта и качества комментария, модуль исполнения тестов и программу расчёта итогового балла. Система оценивает ответы новой модели на фиксированном наборе задач без ручной разметки этих ответов.

## Данные

- Для каждой задачи нужны исходный код, разрешённый контекст, карточка подтверждённого дефекта, описание ожидаемого поведения и скрытые целевые и регрессионные тесты. Модель, выполняющая review, получает код и разрешённый контекст. Оценщик также получает карточку дефекта.
- Для дообучения оценщика нужны ответы нескольких моделей, экспертные метки сопоставления замечаний с дефектом (M) и баллы за качество комментария (C). Независимая целостная оценка H служит ориентиром при валидации итогового CCRQS. См. [инструкцию эксперту](../../contracts/protocol/annotation_guideline_v6.md).

## Расчёт

1. **D — обнаружение дефекта.** Дообученная LLM возвращает метку M для каждого замечания. Программа по этим меткам выделяет замечание, сопоставленное с основным дефектом, и считает D по действующему правилу учёта обнаружений, пропусков и ложных замечаний. Карточка описывает основной дефект. Для других замечаний требуется проверить обоснование по коду или воспроизвести контрпример, чтобы отличить дополнительный реальный дефект от ложного срабатывания.
2. **C — качество комментария.** Та же LLM выставляет отдельные баллы от 0 до 2 за конкретность, корректность объяснения и полезность действия для сопоставленного комментария. Программа нормирует сумму до диапазона от 0 до 1.
3. **Q — качество исправления по тестам.** Пайплайн применяет патч из сопоставленного замечания к исходной версии и запускает скрытые тесты в изолированной среде. Предлагаемая формула автоматической версии — $Q_{\mathrm{auto}}=A\cdot T\cdot R$, где $A$ отражает применимость патча и синтаксическую корректность, $T$ — прохождение всех целевых тестов, $R$ — долю сохранённых регрессионных тестов. При отсутствии подходящего патча $Q_{\mathrm{auto}}=0$. Сбой среды фиксируется как пропуск. В прежнем протоколе был дополнительный множитель S — экспертная оценка смысловой корректности. При расчёте только по тестам чувствительность к некорректным патчам зависит от покрытия тестами. См. [EvalPlus](https://arxiv.org/abs/2305.01210).
4. **Итог.** Для каждого ответа программа считает $CCRQS_i=w_D D_i+w_C C_i+w_Q Q_{\mathrm{auto},i}$. Веса фиксируются до итоговой проверки. Для модели публикуются средний CCRQS на общем наборе задач, средние D, C и Q, а также доля ответов с рассчитанным баллом. Правила учёта невалидных ответов, отказов оценщика и технических сбоев фиксируются до сравнения моделей.

## Проверка на новых моделях

| Часть данных | Что содержит | Для чего используется |
|---|---|---|
| Обучение | Группы задач, ответы нескольких моделей, экспертные M и C | Дообучение LLM-оценщика |
| Настройка | Другие группы задач и экспертные оценки | Выбор контрольной точки, инструкций и правил расчёта. Если подбираются веса по H, используется H этой части данных |
| Итоговая проверка | Отложенные группы задач. На них собираются ответы уже представленных моделей и хотя бы одной модели, ответы которой целиком исключены из обучения и настройки | Оценка согласия с экспертами после фиксации оценщика, весов и тестов. Результаты для отложенной модели анализируются отдельно |

Все ответы на одну задачу и близкие варианты кода попадают в одну часть данных. Для итоговой проверки на тех же ответах запускают два независимых процесса. Автоматический конвейер рассчитывает D, C, Q и CCRQS. Эксперты, которым скрыты автор ответа и автоматические баллы, выставляют M и C для диагностики компонентов. Отдельные эксперты выставляют H всему ответу, включая замечания и патчи. H используется для проверки согласия с итоговым CCRQS, например по корреляции Спирмена с доверительным интервалом. Для проверки ранжирования самих моделей сравнивают разницы между их оценками на общих задачах.

Ошибка сопоставления может изменить сразу D, C и Q. Поэтому дополнительно оценивают C и запускают проверку патча для комментария, выбранного экспертами. Это позволяет оценить качество этих этапов при верном сопоставлении. Для Q проверяют чувствительность скрытых тестов на заранее подготовленных ошибочных патчах и при возможности сопоставляют результат с экспертной S на контрольной подвыборке. Смысловая проверка нужна для эксперимента и не входит в автоматический расчёт.

Дообученную LLM сравнивают с той же базовой моделью, которая работает по тем же правилам оценки без дообучения. Пользу дообучения и перенос на другие модели нужно установить экспериментально. QuixBugs подходит для технической проверки, а вывод о переносе на новые проекты требует корпуса с независимыми группами репозиториев. В обычном прогоне после валидации автоматически оцениваются ответы новой модели на зафиксированном наборе задач.
