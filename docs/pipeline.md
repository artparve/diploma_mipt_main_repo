# Минимальный конвейер CCRQS — этап 8

## Что уже работает

`pipeline.py` загружает локальный QuixBugs, формирует одинаковый содержательный prompt, получает ответ через replay или адаптер локального llama.cpp, сохраняет исходный ответ и структурированный JSON, проверяет контракт v4, применяет каждый diff отдельно к исходному buggy-коду, запускает pytest и три анализатора, вычисляет A/T/R и сохраняет результаты в JSON и SQLite. Конфигурация, хеши, версии пакетов, время и служебные ответы backend остаются в каждом запуске.

Проверены 40 задач. **31 задача** имеет хотя бы один падающий целевой и один проходящий регрессионный тест; эталон проходит обе группы. Шесть задач не имеют проходящих регрессионных тестов: `minimum_spanning_tree`, `next_permutation`, `shortest_path_lengths`, `shortest_paths`, `topological_ordering`, `wrap`. Ещё три — `bitcount`, `find_first_in_sorted`, `sqrt` — не дали полного отчёта на Windows с лимитом 2 секунды на тест; это инфраструктурные исключения, а не нулевые оценки модели. Статусы по каждой задаче зафиксированы в [манифесте](../data/manifest.jsonl).

Эти числа относятся только к текущему техническому окружению. В контейнере перед оценкой патча baseline и reference проверяются повторно по зафиксированным ID тестов. Изменение лимитов или набора тестов требует новой версии manifest и фиксации причин.

QuixBugs используется для отладки: все 40 задач принадлежат **одной группе репозитория**, без разделения на train/calibration/test. Это не основная выборка реальных проектов и не пилот сравнения моделей. [Источник датасета](https://github.com/jkoppel/QuixBugs), commit `4257f44b0ff1181dedaedee6a447e133219fcebf`; Python-часть скопирована из чистого локального checkout. Лицензия и правовые примечания сохранены, все 177 скопированных файлов имеют SHA-256 в `data/provenance.json`. Есть 40 различных хешей исходных задач; это проверка точных копий, не семантическая дедупликация других датасетов.

## Запуск

Установите зависимости и загрузите QuixBugs по инструкции из [README](../README.md). Из корня репозитория запустите:

```sh
python pipeline.py run --config configs/smoke.json
python pipeline.py run --config configs/edge_cases.json
```

`smoke` проверяет обработку эталонных патчей. `edge_cases` включает пустой ответ, неприменимый diff и повреждённый JSON. Оба локальных режима предназначены для доверенных фикстур.

### Docker

```sh
docker build -t ccrqs-runner:v8 .
python pipeline.py run --config configs/smoke.docker.json
python pipeline.py run --config configs/edge_cases.docker.json
```

Контейнер запускает worker без сети, с непривилегированным пользователем, файловой системой и тестами только для чтения и с ограничениями ресурсов. Результаты сохраняются в отдельный каталог. Для запусков реальных моделей подготовьте `configs/llama.local.json` на основе [шаблона](../configs/llama.example.json) и укажите проверенную ревизию модели и backend. Шаблон фиксирует входной лимит, параметры генерации и требования к допуску. [Реестр кандидатов](model_registry_v7.json) описывает рассматриваемые модели.

`pipeline.py prepare` пересоздаёт технический манифест и результаты приёмки, а `pipeline.py fixtures` пересоздаёт эталонные replay-фикстуры. Для новой приёмки используйте отдельную рабочую копию, чтобы сохранить состояние предыдущего прогона.

## Метрики и ошибки

- **A** = diff применился без fuzzy matching и итоговый файл прошёл синтаксическую проверку AST. Допустим только один исходный Python-файл, совпадающий с `issue.file`; абсолютные пути, `..`, второй файл и изменения тестов запрещены.
- **T** = прошли все целевые тесты, которые падали на buggy и проходили на reference.
- **R** = доля сохранившихся проходящих регрессионных тестов из frozen manifest. Пропавший/пропущенный тест и ошибка setup дают инфраструктурный статус, а не R=0.
- **Q** = A·T·R·S. При отсутствии patch, A=0 или T=0 соответствующий issue получает Q=0; иначе S и Q остаются `null` до экспертов. A/T/R измеряются для каждого предложенного patch; итоговый Q review определяется после содержательного сопоставления M, а не средним всех patch.
- **D/C/S/H** не присваиваются по совпадению строк или эталонного diff. Нужны независимые эксперты по протоколу v6. Полный CCRQS остаётся `null`, кроме валидного пустого review с измеримым baseline: D=C=Q=CCRQS=0 по протоколу.

Необычные ответы сохраняются полностью. Допустимо снять только одну внешнюю Markdown-обёртку, при этом `canonical_format_valid=false`. Ошибка JSON/схемы, дублирующиеся ключи, NaN и лишний текст дают `manual_extraction_required`. Автоматической ручной разметки и новых запросов на ремонт JSON нет. Семантические ошибки путей/диапазонов отмечаются отдельно; замечание сохраняется для M.

Инфраструктурный сбой исполнения повторяется один раз. Для inference транспортная ошибка/HTTP 5xx также допускает один повтор; ошибка конфигурации и HTTP 4xx не повторяются. Полученный ошибочный JSON не вызывает повтор генерации. Исходный и повторный отчёты сохраняются; итоговые недоступные показатели имеют `null`. Перед сравнением моделей исключение/повтор должно применяться симметрично к одному и тому же instance. Доля корректного формата считается только среди полученных ответов; число полученных ответов сохраняется отдельно от числа запрошенных задач.

Ruff использует F821/F823, Pylint — E0601/E0602. Технический профиль Bandit: B102/B307/B602/B603/B604/B605/B606/B607/B608/B609, без фильтра severity/confidence. Правила фиксируют кандидатов, а не автоматически подтверждённые дефекты. Каждый анализатор получает исходный и отдельно исправленный код; сохраняются сырые stdout/stderr, версии, команды, время и нормализованные диагностики. При ошибке анализатора его результат получает `infrastructure_error`; полный CCRQS анализаторам не назначается. Профили относятся к техническому QuixBugs-прогону, основной набор правил ещё требует утверждения области дефектов.

## Файлы результата

`data/manifest.jsonl` — машинный manifest с ID целевых и регрессионных тестов; `data/dataset_manifest.csv` — краткий индекс; Команда prepare при новом запуске создаёт локальные baseline/reference-отчёты. `prompts/review.txt` скопирован из v7. Схема ответа и экспертные материалы находятся в [contracts](../contracts/).

Каждый `runs/<run_id>/` содержит `config.json`, `environment.json`, `summary.json`, `results.sqlite` и отдельные каталоги экземпляров. В SQLite таблица `reviews` хранит review_id, instance_id, флаг synthetic, статус и полный result_json; issue_id имеет вид `review_id:issue_index`. В каталоге экземпляра находятся prompt, raw_response, validation, structured_response, baseline/reference отчёты и отдельные `issue_<index>/` с patch, выполнением и A/T/R. HTTP-запуск дополнительно сохраняет props, отформатированный prompt и исходные request/response генерации. Исходный датасет не изменяется при прогоне; его хеши проверяются перед каждым запуском.
